# Правила безопасности и работы с данными (ПДД платформы)

> **Как пользоваться:** блок 7б каждой карточки ЦА содержит top-4 правила из раздела «Красный» ниже + риски специфичные сегменту. Полный реестр — здесь. Обновляется централизованно; при изменении не требует правки карточек.

---

## Красный — критические правила (inline в карточки)

Эти четыре правила обязательны для понимания перед первым запуском. Каждое нарушение — реальный риск: утечка данных, потеря работы, блокировка доступа, разрыв ожиданий.

### R1. Собственный контроль над данными

**Правило:** платформа не хранит ваши рабочие данные (конспекты, стратегии, код) на своих серверах. Вы храните их в своём экзокортексе (Obsidian, Notion, GitHub) под своим контролем. Платформа даёт метод, память и ритм — но не владение файлом.

**Что делать:** держать основной бэкап в собственном хранилище. Использовать GitHub для версионирования критичных артефактов.

**Что НЕ делать:** не хранить в чате с агентом (Claude, Kimi) конфиденциальные данные без явного consent'а. Чаты — оперативная память, не архив.

### R2. Граница личного и корпоративного

**Правило:** если вы работаете в компании — данные компании остаются в инфраструктуре компании. Доступ к корпоративным системам через личный экзокортекс допустим только при явном разрешении работодателя.

**Что делать:** при использовании IWE для рабочих задач — согласовать с работодателем или использовать отдельное, изолированное хранилище.

**Что НЕ делать:** не загружать конфиденциальные документы компании в личные инструменты без разрешения. Это риск для вас и для компании.

### R3. Публикация и публичная видимость

**Правило:** всё, что вы отправляете в публичный канал (марафон, клуб, GitHub, блог), становится видимым. Отдельные материалы (стратегия, личные рефлексии) по умолчанию остаются приватными.

**Что делать:** перед публикацией — явно спросить себя: «что будет, если это прочитает мой работодатель / клиент / конкурент?» Использовать peer-review перед публикацией чувствительного контента.

**Что НЕ делать:** не публиковать чужие данные без consent'а. Не раскрывать в публичном канале закрытую информацию о компании.

### R4. Consent и сбор данных

**Правило:** платформа собирает traces (consent-based) для персонализации работы агентов и ритмов. Opt-out доступен в любой момент через настройки. Данные хранятся в вашем цифровом двойнике; доступ — только вам и вашим агентам.

**Что делать:** прочитать условия сбора данных при первом входе. Знать, где находится переключатель opt-out.

**Что НЕ делать:** не предполагать, что платформа «ничего не собирает» — будьте информированы, чтобы выбор был осознанным.

## Жёлтый — правила конкретных ситуаций

### Y1. Работа с API-ключами и токенами

- API-ключи Claude/Kimi хранить в `.env` или менеджере секретов (не в коде, не в чате).
- При коммите — pre-commit hook проверяет отсутствие секретов (настраивается в репо).
- Утечённый ключ — немедленно отозвать и сгенерировать новый.

### Y2. Сессии и токены доступа

- Сессия агента — временная. Не рассчитывать, что агент «помнит» между сессиями (если не настроена персистентная память через MCP/Neon).
- Токены доступа к Discord/Slack/боту — хранить в защищённом хранилище, не передавать в общие чаты.

### Y3. Резервное копирование

- Экзокортекс (Obsidian-vault, репо) — ежедневный bkp через git commit + еженедельный архив в облако.
- Стратегические документы — две копии (локальная + GitHub/private cloud).

## Зелёный — рекомендации

### G1. Принцип наименьших привилегий

- Давайте агентам минимально необходимый доступ. Не подключайте MCP с полным доступом к файловой системе, если достаточно scoped доступа к папке проекта.

### G2. Регулярный аудит доступов

- Раз в квартал — проверка: кто имеет доступ к вашим репо, какие приложения подключены, какие токены активны.

### G3. План B при недоступности платформы

- Ваши данные — в вашем хранилище. Если платформа недоступна — вы продолжаете работать в Obsidian/GitHub без потери контекста. Это не vendor lock-in.

## Сегмент-специфичные риски (добавляются в блок 7б карточек)

| Сегмент | Специфичный риск | Как адресовать |
|---------|------------------|----------------|

| A2 (ИТ) | API-ключи в коде/чате | Y1 + pre-commit hook |
| K (руководитель) | Корп. данные в личных инструментах | R2 в приоритете + отдельный workspace для команды |
| C (база) | Завышенные ожидания от ИИ-помощника | R4 + онбординг-момент: платформа = метод + ритм, не волшебный сервис |
