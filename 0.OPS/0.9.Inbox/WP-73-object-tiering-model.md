# Модель тиров объектов IWE (общеплатформенное / общекомандное / личное)

> **Назначение.** Ответить на три вопроса: (1) что в экосистеме общее для платформы, что для команды, что уникально участнику; (2) как разработчик пака / графа понятий / руководства / кода работает в команде; (3) как объект разлетается по домам (Мир/Россия) и языкам. Основано на инвентаризации ~90 объектов и диалоговой сессии Claude + Kimi.
>
> **Статус:** черновик на ратификацию с командой.

<details open>
<summary><b>0. Главное за 30 секунд</b></summary>

- Объекты делятся на два **рода**: **доставляемый артефакт** (копируется в каждую установку — пак, скилл, база стиля, правило) и **работающий сервис** (один инстанс, к нему подключаются — бот, MCP-сервер, шлюз).
- **Артефакт** имеет тир: **платформенный** (всем пользователям IWE), **командный** (нашей команде разработки), **личный** (одному участнику). У командных есть пометка трека (А/В).
- **Сервис** описывается тройкой: дом (Мир/Россия/канон/личное) × трек (А/В) × тенантность (один общий инстанс / на пользователя).
- Тир задаётся **обещанием** (кому объект адресован), а не тем, где файл лежит сейчас. Разрыв «обещан платформе, фактически у команды» допустим только под оформленную задачу промоции со сроком.
- Три оси не путать: **тир** (кто разделяет) ≠ **дом** (где живёт по Мир/Россия) ≠ **трек** (какой продукт обслуживает). Трек А/В — продуктовая ось, не географическая.

</details>

<details>
<summary><b>1. Два рода объектов: артефакт и сервис</b></summary>

Главное различение, без которого классификация ломается на ботах и MCP-серверах.

- **Доставляемый артефакт** копируется/доставляется в каждую установку: паки, скиллы, базы стиля, правила, хуки, протоколы. Вопрос к нему: «кому этот объект доставляется?» → тир совместности.
- **Сервис** — это один работающий инстанс, к которому подключаются много пользователей: боты, MCP-серверы, воркеры, шлюз. Вопрос к нему: «где он работает, какой продукт обслуживает, где граница пользователей на одном инстансе?» → дом × трек × тенантность.

**Почему это нужно.** В каталоге бот марафона помечен «платформенный · российский · трек А» — платформенный, но трек-специфичный. Для артефакта это противоречие (платформенное = для всех = оба трека). Для сервиса противоречия нет: бот — один мультитенантный инстанс в российском доме, обслуживает трек А. «Платформенность» сервиса = «общий инстанс на многих», а не «копия у каждого».

**Смешанный репозиторий** (код сервиса + его документация-артефакт в одном git-хранилище) инвентаризуется построчно: код = строка-сервис, документация = строка-артефакт. Инвентаризуем объекты, не хранилища-монолиты.

</details>

<details>
<summary><b>2. Тир доставляемого артефакта</b></summary>

| Тир | Кто разделяет | Канал доставки | Примеры |
|-----|---------------|----------------|---------|
| **платформенный** | все пользователи IWE везде | шаблон движка (FMT) → update.sh | базы стиля L0, 39 базовых скиллов, протоколы ОРЗ, FPF/SPF/ZP, базовые хуки, formatting.md |
| **командный** | наша команда разработки (А + В) | командные репо (`iwe-platform`, `mim-school`, governance) | канонический набор паков, граф понятий (артефакт), SYNC-CORE, реестр репо |
| **личный** | один участник | остаётся локально, не доставляется | персональное руководство, авторские надстройки L1/L3, персона, память, личный governance-хаб |

**Правило отнесения (тест):** «Получит ли новый внешний пользователь IWE этот объект через update.sh без доп. настройки?» Да → платформенный. «Нужна ли для него наша командная экосистема (наш набор паков, мультиагент)?» Да → командный. «Уникально для одного человека?» → личный.

**Обещанный тир ≠ фактический.** Тир = кому объект **адресован** (суть), а не где файл лежит сейчас. Поэтому у артефакта два поля:
- `target_tier` — кому адресован (стабильно).
- `current_tier` — где фактически доставлен.
- **Разрыв** (`target` ≠ `current`) легитимен ТОЛЬКО при оформленной задаче промоции: есть РП/фаза + владелец + критерии приёмки + срок ≤ 2 контрольных точки. Иначе `current_tier` = факт, и «обещание платформе» не засчитывается. Это не даёт объектам годами висеть «как бы платформенными».

Пример разрыва: инжектор инженерного стиля и движок правил реализуют платформенные обещания, но физически ещё не в шаблоне → `target=платформа, current=команда, delivery_gap` под отдельную задачу промоции.

</details>

<details>
<summary><b>3. Классификация сервиса</b></summary>

Сервис не «доставляется» — к нему подключаются. Три измерения:

- **Дом:** мировой (инфраструктура Мир) / российский / канон-IWE / личный.
- **Трек:** А / В / оба.
- **Тенантность:** один общий инстанс на всех (multi-tenant) / инстанс на пользователя (per-user) / одиночный.

| Сервис | Дом | Трек | Тенантность |
|--------|-----|------|-------------|
| Умный поиск, цифровой двойник, личное знание (MCP) | мировой | оба | общий, изоляция по пользователю |
| Шлюз (Aisystant MCP) | мировой | В | общий |
| Локальный шлюз (мультиагент в VS Code) | канон | оба | на пользователя |
| Бот марафона, веб-ридер руководств, воркер проекций | российский | А | общий |
| Портной (генерация руководств) | российский | А | общий |

</details>

<details>
<summary><b>4. Три оси — не путать</b></summary>

Корень путаницы (мы спотыкались три сессии): объект описывается тремя независимыми координатами.

- **Тир (кто разделяет):** платформа / команда / участник — только для артефактов.
- **Дом (где живёт по Мир/Россия):** мировой / российский / канон / личный — для всех.
- **Трек (какой продукт):** А / В / оба — атрибут командных артефактов и всех сервисов; для платформы всегда «оба», для личного «никакой», поэтому отдельной осью у них не нужен.

Плюс колонка **владелец** (Церен / Андрей / Ильшат / Паша / команда) как метаданные, не ось.

</details>

<details>
<summary><b>5. Треки А и В — продуктовая ось, не географическая</b></summary>

Важное (переопределение в стратегии 19 мая): **Track B — это не «только мир», а основной продукт для всех новых пользователей, включая россиян.**

- **Трек А** = старый контур: учебная платформа (LMS) + бот @aist_me_bot + существующие российские подписчики. Владелец после передачи — Ильшат. Рубли, российская инфраструктура.
- **Трек В** = новый продукт IWE: единая воронка от лендинга до VS Code, для любого нового пользователя любой географии. Мировая инфраструктура (Google Kubernetes + европейский вход). Владелец — Церен + автономные агенты.

Поэтому россиянин-новичок попадает в трек В, а не А. Связка «трек = страна» — ложная. Дом (где инфраструктура) и трек (какой продукт) — разные оси.

</details>

<details>
<summary><b>6. Как разработчик работает в команде — по ролям</b></summary>

- **Разработчик пака.** Пишет доменный пак = **командный артефакт** (канон, оба трека) в `iwe-platform`. В шапку единиц ставит коды понятий. Базовые принципы (FPF/SPF/ZP) приходят ему как **платформенный артефакт** через update.sh. Его пак доезжает до товарищей по команде через командный репо.
- **Разработчик графа понятий.** Правит **командный артефакт** (граф = канон). Изменение термина запускает анализ влияния по ссылкам. Доступ к графу для всех — через сервис умного поиска (**платформенный сервис**, мультитенант). Артефакт и сервис-доступ — два объекта.
- **Разработчик универсального руководства.** Пишет артефакт (контент в `aisystant/docs`, мировой дом). Конвейер собирает языковые и регистровые проекции. Доставка читателю — через сервис-ридер. Контент и канал — разные объекты.
- **Разработчик кода/сервиса.** Строит **сервис**: классифицирует по дом × трек × тенантность. Канонический код методов → `iwe-platform`; российский сервис → российская инфраструктура; секреты деплоя → приватный `iwe-sync`, не в коде.
- **Личная сборка любого участника.** Свои надстройки стиля (L1), личные скиллы (L3), персона, память, личный хаб = **личный тир**, остаётся локально, не реплицируется другим. Это «костюм» участника поверх общего оснащения (различение Костюм ≠ Оснащение).

</details>

<details>
<summary><b>7. Как объект разлетается по местам и языкам</b></summary>

Только артефакты «разлетаются»; сервисы стоят на месте, к ним подключаются.

Один канонический артефакт расходится по трём осям проекции (механизм — конвейер синхронизации, см. `WP-73-iwe-sync-conventions.md`):
1. **Язык** — граф понятий собирает английскую версию рядом с русской.
2. **Регистр и аудитория** — база стилей собирает версии под аудиторию.
3. **Площадка** — витрины (мировой дом) тянут английскую версию; российский дом тянет русскую + российскую надстройку.

Тир при этом сохраняется: платформенный артефакт остаётся платформенным во всех проекциях; меняется только дом и язык конкретной проекции.

</details>

<details>
<summary><b>9. Что делать дальше (механизм)</b></summary>

1. **Ввести поле `audience: platform | team | participant`** в метаданные артефактов (обобщает существующий `layer: L1/L3` у скиллов). Это классификация; новый слой в трёхслойной модели CLAUDE.md НЕ заводим.
2. **Признать командный канал доставки** — командные репо (`iwe-platform`, `mim-school`, governance). Платформа → шаблон/update.sh; команда → командные репо; участник → локально.
3. **Реестр разрывов доставки** — список объектов `target≠current` с задачей промоции, владельцем, сроком. Без задачи объект числится по факту.
4. **Починить мисфайл** — командные правила (SYNC-CORE), лежащие в платформенном слое, пометить `audience: team`.
5. Сервисы инвентаризовать отдельным реестром (дом × трек × тенантность), не смешивая с артефактами.

</details>
