# Предложение: защищённый контракт чтения потоков для «Рабочего места наставника» (РП-578)

## Кому

Команда платформы (LMS/CRM, `aisystant/aisystant`) — контакт Наталья Бакулина.

## Контекст

Строим отдельный сервис для наставника (карточка участника, архив переписки, помощник ответа, табло потока — РП-578). Часть нужных данных уже существует в платформе, но сегодня нет безопасного способа их прочитать из другого сервиса. Разбор вёлся в пир-сессии `MC-sessions:2026-09/18/2026-09-18-08-svyaz-rabochego-mesta-nastavnika/` (Claude+Kimi+Codex, живое чтение кода `aisystant/aisystant`).

## Что нужно

Новый эндпоинт для сервисного (не пользовательского) доступа, примерно:

```
GET /api/integration/v1/mentorship/streams
```

С сервисной авторизацией (не cookie/Session-Token обычного пользователя — отдельный service account или подписанный токен), пагинацией и версией/курсором для инкрементальной синхронизации. По каждому потоку, назначенному вызывающему сервису:

- `potok_id`, код, название, статус, даты начала/окончания;
- `telegram_chat_id` — **из поля `Potok.tgId`** (числовой ID группы, уже используется монолитом для поиска потока по входящему сообщению), **не из `Potok.chatLink`** (это отдельное необязательное текстовое поле-приглашение для человека, не участвует в сопоставлении и может быть пустым/устаревшим);
- назначения наставников на поток (кто наставник/пилот этого потока);
- состав участников со стабильным идентификатором (`suser_id`) и, если это укладывается в периметр данных, привязанным `tg_id` участника.

## Чего НЕ просим

- Не просим доступ на запись — только чтение.
- Не просим менять экран `/lk/#/teacher/` или его код (`gitlab.com/aisystant/aisystant-front`) — наша поверхность строится отдельно.
- Не просим текущий открытый `GET /api/crm/potok` расширять — он для другой аудитории и, отдельно от этого предложения, имеет проблему доступа (см. ниже).

## Побочная находка при разборе (сообщена отдельно)

`GET /api/crm/potok` сегодня не требует авторизации вообще, а `GET /api/crm/potok/{id}/course-passing` не проверяет, что вызывающий наставник назначен именно на этот поток. Передано Наталье отдельным сообщением 18.09 — не часть этого предложения, но связано с тем же участком кода.

## Зачем это нам

Без этого контракта наш сервис ведёт свою временную копию списка потоков и их состава, а привязка телеграм-чата к потоку делается наставником вручную командой в боте. Это рабочий, но временный путь (см. карточку `DS-my-strategy/inbox/WP-578/WP-578.md`, разделы Ф1/Ф2) — с контрактом выше ручная регистрация становится резервным способом, а не единственным.
