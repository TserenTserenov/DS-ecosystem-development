# ТЗ: серверный сервис подписки на паки (РП-532 Ф4)

> **РП:** [WP-532](https://github.com/TserenTserenov/DS-my-strategy/blob/main/inbox/WP-532/WP-532.md) (DS-my-strategy). Адресат — Андрей, владелец серверных MCP-инструментов (инфраструктура передана 12.08).
> **Источник:** АрхГейт-эквивалент, пир-сессия с Codex 15.08 (`sessions/2026-08/15/2026-08-15-06-wp532-f4-archgate-server-subscription/`, DS-my-strategy) + это техзадание, пир-сессия с Codex 16.08 (`sessions/2026-08/16/2026-08-16-01-codex-canaccesspack-observe-warn/`, DS-my-strategy).

## Цель

Работа с паками (доменное знание) в браузере claude.ai и в боте, не только в VS Code — тот же уровень возможностей, что уже есть локально: увидеть каталог, подключить/отключить пак, увидеть что уже подключено, управлять составом поиска. Сейчас браузер и бот де-факто «работают с паками» только потому, что серверный поиск открыт всем без разбора (найденный дрейф, 15.08) — это и есть дыра, которую закрывает эта работа.

## Архитектурное решение (АрхГейт-эквивалент пройден 15.08, пир-сессия с Codex)

Единая серверная точка проверки доступа **`canAccessPack(user, pack)`** — обязательна для ВСЕХ путей чтения содержимого пака: поиск, прямой source lookup, кеши, re-rank/summary-пайплайн, не только `knowledge_search`. Без единой точки другие входы остаются дырой независимо от того, насколько хорошо защищён основной путь.

## Компоненты

### 1. Хранилище подписок

Таблица `pack_subscriptions(subscriber, pack)` — простая, без преждевременного обобщения до `content_subscriptions`. Данные («что подписано») хранятся отдельно от решения о доступе (`canAccessPack` читает эту таблицу, но логика проверки в ней не живёт).

### 2. `canAccessPack(user, pack)`

Порядок проверки: сначала реальная подписка (`pack_subscriptions`), затем — если подписки нет — grace-исключение (см. §4), с обязательной меткой `reason` в лог при срабатывании grace. Все три серверных инструмента (см. §3) и фильтр поиска (см. §5) идут через эту функцию, не мимо и не дублируя логику локально.

### 3. Три серверных инструмента

- показать каталог (+ что уже подключено — либо часть того же вызова, либо отдельный пункт);
- подключить пак;
- отключить пак.

Все три — через `canAccessPack`.

### 4. Bootstrap для старых пользователей шлюза (решение пилота 16.08)

**Grace-list ≠ auto-subscribe.** Это два разных механизма:
- `pack_subscriptions` — перманентное право, запись создаётся только явным действием пользователя (подключение пака);
- `grace_access` — отдельная сущность, временное исключение только для enforcement-слоя, не меняет систему настоящих прав:

```
grace_access(
  user,
  scope_pack | scope_all,
  start_at,
  end_at,
  reason,
  created_by,
  created_from_cutover
)
```

**Источник истины — материализованный снимок, не логи.** На старте стадии `observe` (см. §6) — разовый cutover-job: снимает список пользователей, у которых уже был фактический доступ к пакам через шлюз, и заполняет `grace_access` явными записями (не «виртуальный список» из логов — окна наблюдения и пропуски телеметрии делают логи ненадёжным источником для продового перехода). У job фиксируются: timestamp cutover, источник данных, ответственный за запуск.

**Bootstrap-процедуре запрещено** создавать или изменять записи в `pack_subscriptions` — только в `grace_access`.

### 5. Фильтр в существующем поиске

`knowledge_search` / `knowledge_list_sources` вызывают `canAccessPack`, не дублируют проверку локально. Это чинит найденный 15.08 дрейф: серверный шлюз индексирует все 11 паков (включая приватный и «невыдаваемые» внутренние) и сегодня отдаёт их всем без разбора.

### 6. Поэтапное включение

`observe` (лог без блокировки) → `warn` → `enforce`, плюс kill switch. Не одномоментное включение для всех текущих пользователей шлюза.

**Cutover-job и сверка перед `enforce`:** до перехода из `warn` в `enforce` — job, который проверяет по каждому пользователю из `grace_access`, готов ли он к полному включению правил, и формирует отчёт (кто пройдёт, кто нет, почему). Критерий готовности — **открытый вопрос, см. §7**.

**Per-user postpone enforce** допустим только с явным сроком действия (TTL) и назначенным ответственным — не бессрочная отсрочка.

### 7. Открытый вопрос — решает пилот, не эта сессия

При сверке перед `enforce` нужно проверить, что у grace-пользователя есть настоящая подписка. Черновая формулировка пилота — «сверяем подписку на пак МИМ» — можно прочитать двумя способами, и они дают разный результат для разных пользователей:

- **Вариант А:** пак МИМ (мастерская инженеров-менеджеров) — обязательный базовый пак для всех, кто в grace-list, независимо от того, каким пакам он реально пользовался. Отсутствие подписки на МИМ = сигнал неготовности для этого пользователя.
- **Вариант Б:** сверка идёт по целевому набору паков конкретного пользователя (то, чем он реально пользовался до cutover), а МИМ упомянут пилотом просто как пример/самый частый случай, не как универсальный критерий.

Разница практическая: при варианте А пользователь, который легитимно пользовался только другими пакерами (не МИМ), будет ошибочно считаться неготовым к `enforce`. Этот пункт не блокирует старт реализации §1-6 — он всплывает только на шаге сверки перед `enforce`, который в очереди последний.

### 8. Kill switch

Гибрид, не только ручной и не только автоматический:

- **Ручной глобальный рубильник.** Основной ответственный — пилот; если пилот недоступен дольше 2 часов при активном алерте — Андрей (владелец инфраструктуры).
- **Автоматический триггер** на стадиях `warn`/`enforce` по SLO-порогам (рост deny-ответов, latency, error-rate) — действие «понизить строгость» (`enforce → warn`), не безусловный полный откат.
- **Operational target:** реакция на срабатывание (ручное или автоматическое) — в пределах **2 часов, отсчёт с момента алерта/инцидента**, в рабочее время (часовой пояс и окно уточнить при передаче — не зафиксированы в этой сессии, редакционная деталь). Best-effort вне рабочего времени, формального круглосуточного SLA на первом прогоне не даём.
- **Защитный дефолт:** если и пилот, и Андрей недоступны дольше 2 часов при активном алерте — автоматический откат `enforce → warn` (понижение строгости, не полное отключение).
- На стадии `observe` operational-требование не действует — стадия только логирует, ничего не блокирует.

### 9. Бот

Получает те же три инструмента (§3) через тот же серверный бэкенд, что и браузер — разный только интерфейс показа, логика одна.
