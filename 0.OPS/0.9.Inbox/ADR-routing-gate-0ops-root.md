# ADR-draft: серверный гейт размещения — запрет новых файлов в корне `0.OPS/`

## Проблема

Мета-уровень `0.OPS/*` (F0) = операционная governance + транзит обсуждения, НЕ дом доменного знания и не дом кросс-ядерной навигации. Постоянные дома = Паки + ядра `A/B/C`. Но карта `DP.KR.001 §5` — это поведенческий гейт (можно проскочить). Нужен механический серверный гейт.

## Почему серверный, не локальный

Различение «серверный замок ≠ локальный хук»: локальный pre-commit в командном репо ловит только того, кто его себе поставил — «личный замок в маске командного». Командный enforcement = серверная проверка при заливке (CI / pre-receive), ловит всех участников.

## Предлагаемое правило (узкое, низкий FP)

При заливке в `aisystant/DS-ecosystem-development`: **новый файл (`A`/`R`-в) прямо в корне `0.OPS/*.md`** (не в подпапке `0.1`-`0.99`) → блок.

- В корне `0.OPS/` живут только реестры (`REPOSITORY-REGISTRY.md`, `numbering-registry.yaml`). Новый файл там = почти наверняка ошибка размещения знания/навигации.
- **Bypass:** тег `[routing-gate-bypass]` в commit-сообщении (для легитимного нового реестра мета-уровня).
- Реализация: GitHub Actions на `pull_request`/`push` в main (или pre-receive, если будет self-hosted).

## Открытые вопросы команде

1. CI (GitHub Actions) или pre-receive? Сейчас GHA доступнее.
2. Расширять ли на другие транзит/мета-локации (`0.7.Plans` — постоянная, не трогать) или держать узким на корень `0.OPS`?
3. Владелец реализации и срок.
