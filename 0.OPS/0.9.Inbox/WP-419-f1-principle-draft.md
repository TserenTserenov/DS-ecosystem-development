# Принцип Ф1: Механизм принуждения как условие принятия схемы кодирования

> **Источник:** peer-сессия 2026-06-12-16. Черновик для Ф4. До финализации не применять к production.

## Основание (empirical)

Инвентаризация ~65 реестров IWE (2026-06-12) показывает:

| Механизм | Наблюдаемая выживаемость |
|----------|-------------------------|
| Физическая структура папок (E0) | ~100% |
| Код читает обязательно, падает без схемы (E1-hard) | ~90% |
| Git-хук/CI блокирует нарушение (E2) | ~80% |
| Код читает опционально, работает без поля (E1-soft) | ~38% |
| Только конвенция/документ (E3) | ~5-15% |

Ключевой вывод: **предиктор выживания схемы — не качество дизайна, а наличие механизма, делающего нарушение дорогостоящим или физически невозможным.**

## Нормативный принцип (Ф1)

> **Схема принята (`status: active`), если выполнены все три условия:**
>
> **(а) Механизм принуждения:** E0, E1-hard или E2.
> E1-soft и E3 → `enforcement: weak`; схема регистрируется с еженедельным coverage-сторожем.
>
> **(б) Поверхность принуждения (enforcement surface):** при регистрации указаны пути записи, НЕ покрытые механизмом, и подтверждено, что они нештатные (нерегулярные).
> Если непокрытый путь используется регулярно → нужен дополнительный E0, E1-hard или E2 на этот путь.
>
> **(в) Два ортогональных слоя принуждения:** в регистрации явно заполнены оба поля:
> - `structural_enforcement`: механизм для «схема присутствует» (E0/E1-hard/E2)
> - `semantic_enforcement`: механизм для «значение схемы корректно» (E0/E1-hard/E2) или `E3-acknowledged: "<что именно не проверяется и почему допустимо>"`
>
> Пустое `semantic_enforcement` ≠ E3-acknowledged. Пустое поле = «решение не принято» → принцип не выполнен.

## Ось механизмов (E0-E3)

| Уровень | Механизм | Enforcement surface | Примеры |
|---------|----------|---------------------|---------|
| **E0** | Физическая структура (OS) | 100% — нарушить невозможно | A./B./C./D.-ядра, X1/X2/X3 позиции |
| **E1-hard** | Код ПАДАЕТ без поля/записи | Покрывает путь чтения; запись нарушенного возможна | executor-catalog (агент не запустится), registry.json (парсер ломается) |
| **E1-soft** | Код ИСПОЛЬЗУЕТ поле если есть | Не покрывает absent-case | `family: F0-F9` (38% заполнения) |
| **E2** | Gate блокирует при нарушении | Покрывает git-flow; не покрывает out-of-band пути | WP-REGISTRY drift-guard, AR-правила в хуках |
| **E3** | Только конвенция/документ | Не покрывает ничего | `epistemic_stage`, naming rules без валидатора |

## Упразднённые исключения

**E3-single (убрано):** E3 «при одном пользователе» — не категория метода:
- «Единственный пользователь» — будущий факт, непроверяемый при регистрации.
- Переход от 1 к N участникам не сопровождается ритуалом пересмотра принуждения → тихая бомба.
- Схема с одним пользователем — либо личная привычка (не регистрируется в реестре), либо уже нужен E2.

## Применение к регистрации новой схемы

Поля регистрации (минимально необходимые для Ф4):

```yaml
schema_registration:
  name: "..."
  owner: "..."                                 # кто отвечает
  enforcement_mechanism: E0 | E1-hard | E2 | E1-soft | E3
  enforcement_surface:
    covered_paths: []                          # список: git-commit, agent-write, api-write...
    uncovered_paths: []                        # что НЕ покрыто
    uncovered_is_nonstandard: true | false     # нештатные пути?
  structural_enforcement: E0 | E1-hard | E2   # механизм для «схема присутствует»
  semantic_enforcement: E0 | E1-hard | E2     # механизм для «значение корректно»
    # ИЛИ:
  semantic_enforcement_e3_acknowledged: "что не проверяется и почему это допустимо"
```

## Связи с Ф4

- Чеклист Ф4 «заводишь новый код/список»: поля выше → обязательный раздел.
- AR-правило (доставка агентам): enforcement_mechanism + enforcement_surface → поля при создании нового реестра в WP Gate.
- Доставка: принцип → PACK-digital-platform; AR-правило → PACK-agent-rules (при Ф4).
