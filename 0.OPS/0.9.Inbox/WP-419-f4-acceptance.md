# Ф4-приёмка: прогон чеклиста метода на реальных кейсах

> **Цель:** проверить, что метод (DP.METHOD.054) правильно различает здоровую схему и сломанную, и применяется сам к себе. Покрывает часть gate §11 (прогон 3 реальных + 1 новый); остаток gate (AR-правило + ИТ-ревью) — за командой.

## Кейс 1 (реальный, сломан): AR.NNN — правила агента

| Поле | Значение |
|------|----------|
| owner | команда agent-rules (PACK-agent-rules) |
| bounded_context | правила поведения агента IWE |
| axis_facet | приоритет 1-10 (ортогонально — ок) |
| enforcement_mechanism | реестр E1-soft/E3 |
| structural_check | weak — 61 файл, 29 в реестре (дрейф) |
| semantic_check | E3 — нет валидатора «реестр = файлы» |

**Итог:** метод корректно диагностирует дрейф → вердикт FIX (реестр под E2 drift-guard). ✅ метод сработал.

## Кейс 2 (реальный, сломан): `family: F1-F9` — семейства документов

| Поле | Значение |
|------|----------|
| owner | команда 0.OPS |
| bounded_context | семейства документов S2R |
| axis_facet | ось «взгляд» — **НЕ ортогональна** FX-оси (коллизия COL-01) |
| enforcement_mechanism | E1-soft (38% заполнено) |
| structural_check | weak |
| semantic_check | E3 — путаница F3/F7 не ловится |

**Итог:** метод вскрывает **оба** дефекта — дизайн (фасет не ортогонален) И принуждение (weak). Это доказывает ценность двух дорожек: одной enforcement-проверки было бы мало. ✅ метод сработал, две дорожки оправданы.

## Кейс 3 (реальный, здоров — контроль): WP-NNN

| Поле | Значение |
|------|----------|
| owner | Стратег (DS-my-strategy) |
| bounded_context | рабочие продукты |
| axis_facet | последовательная нумерация — **классификация НЕ вшита в ID** (хорошо) |
| enforcement_mechanism | E2 (WP-REGISTRY drift-guard) |
| structural_check | E2 ✓ |
| semantic_check | E2 (guard сверяет inbox↔реестр) |

**Итог:** метод подтверждает здоровую схему (E2 + стабильный ID + owner). Контроль: метод НЕ заваливает хорошую схему. ✅

## Кейс 4 (новый): `registry-catalog.yaml` — мета-реестр (самоприменение)

| Поле | Значение |
|------|----------|
| owner | Стратег/команда |
| bounded_context | мета-реестр реестров |
| axis_facet | перечень (не нумерация) |
| enforcement_mechanism | MVP E1-hard (генератор падает) + heartbeat; target E2 |
| structural_check | E1-hard |
| semantic_check | E3-acknowledged: «дрейф каталог↔реальность ловит heartbeat, не write-time — допустимо для редко меняющегося мета-реестра, target E2» |

**Итог:** метод применяется к самому каталогу, вскрывает quis-custodiet и фиксирует E1-hard MVP + E2 target. ✅ самоприменение работает.

## Вывод приёмки

- Прогон 3 реальных (2 сломаны → FIX, 1 здоров → PASS) + 1 новый (самоприменение) — **метод проходит дименсию «прогон чеклиста»**.
- Метод корректно различает здоровое/сломанное и **не даёт ложного PASS** здоровой схеме.
- Кейс 2 эмпирически доказал необходимость двух дорожек (enforcement-only пропустил бы дизайн-дефект).
- **Остаток gate активации (draft→active):** регистрация AR-правила доставки + ревью на ИТ-встрече (командный канон). До этого DP.METHOD.054 остаётся draft.
