# Аргументная карта: коллизии кодирования COL-01..COL-08

> **Назначение.** Подготовка к батч-сессии принятия решений (пилот). Для каждой коллизии: суть, счётчики фактического использования, варианты разрешения, предлагаемый вердикт. Коллизии помечены: 🔴 требует пилота / 🟡 предлагаемый вердикт (пилот подтверждает) / 🟢 автономное решение.
>

## COL-01: F1-F9 ↔ FX1-FX9 (транспонированные матрицы) 🔴

**Суть.** Схема 0.OPS нумерует семейства документов по ролям-взглядам: Meaning=F1-F3, Architecture=F4-F6, Operations=F7-F9. Матрица проектных ролей нумерует по системам: Надсистема=FX1-FX3, Целевая=FX4-FX6, Подсистемы=FX7-FX9. Матрицы транспонированы — единственное совпадение на диагонали (F5=Architecture×Целевая). Это источник хронической путаницы F3/F7 в документации 0.OPS.

**Счётчики использования.**
- `family: F[1-9]` (в frontmatter 0.OPS): ~38% файлов DS-ecosystem-development (~223 из 589 по инвентаризации)
- FX-ссылки как папки: ~100% структуры C.IT-Platform (X1/X2/X3)
- Пересечение: документы внутри FX-папок имеют свой F-семейства frontmatter → систематическое смешение

**Вариант A.** Оставить обе схемы, явно задокументировать как разные пространства имён (F-семейства = ось документов; FX = ось проектных ролей). Обновить 02-document-families.md.

**Вариант B.** Унифицировать: FX1-FX9 переименовать в роли без числовых суффиксов (Надсистема, Целевая, Подсистемы) или ввести составной код (F[system_code][role_code]). Requires: ~50+ файлов переименовать.

**Предлагаемый вердикт.** Нет — архитектурное решение с широким impact. Требует пилота.

**Вопросы к пилоту:**
- Допустимо ли сосуществование двух схем с явной документацией (Вариант A)?
- Стоит ли вводить составной код или унифицировать по одной из осей?

## COL-02: Две раскладки в одном каноне 🔴

**Суть.** В файле `02-document-families.md` (0.OPS) одновременно присутствуют: role-major раскладка (строки = взгляды, столбцы = системы) и альтернативная system-major (строки = системы, столбцы = взгляды). Оба варианта показывают одно и то же содержимое, но разными осями. Источник путаницы «какая из двух правильная?»

**Счётчики.** ~1 файл (сам 02-document-families.md), но ссылки на него — во всех материалах 0.OPS-онбординга.

**Вариант A.** Удалить одну раскладку, оставить role-major как основную (совместима с нумерацией F1-F9).

**Вариант B.** Оставить обе, явно подписать назначение каждой (основная / справочная).

**Предлагаемый вердикт.** Нет — связан с COL-01. Решается вместе.

**Вопросы к пилоту:** Какая раскладка интуитивно «правильная»? (role-major или system-major?)

## COL-03: `C.` = Component ↔ C = ядро ИТ-платформы 🟡

**Суть.** Префикс сущности `C.` (из схемы префиксов 0.OPS: C=Component) vs буква `C` как обозначение ядра ИТ-платформы в структуре папок DS-ecosystem-development (`C.IT-Platform/`).

**Счётчики.**
- `C.` как entity prefix: ~6 файлов (почти нет использования)
- `C` как обозначение ядра: ~100% структуры (папки C.IT-Platform, ссылки в документах)

**Предлагаемый вердикт.** Разделить по области видимости (scope):
- `C.` (с точкой) = префикс сущности Component в схемах/конфигах. Использования нет — можно отменить как мёртвый.
- `C` (без точки) = буква ядра ИТ-платформы в структуре папок. Канон, трогать нельзя.
- Ловушка: никогда не использовать `C.` как ссылку на ядро в текстах — только `C.IT-Platform` (полное имя).

**Нужен пилот:** только для подтверждения отмены `C.` entity prefix как мёртвого.

## COL-04: `F5` family ↔ `F: 5` formality (Trust Calculus) 🟢

**Суть.** Поле `family: F5` (семейство документа — Architecture×Целевая) vs поле `F: 5` (formality из Trust Calculus) встречаются в одном frontmatter-шаблоне.

**Счётчики.**
- `family: F5`: 83 файла (активное использование)
- `F: N` (Trust Calculus formality): 0 файлов (полностью мёртвое)
- Смежное: `trust:` = 29 файлов, `epistemic_stage:` = 24 файла — все мёртвые хвосты

**Предлагаемый вердикт.** Автономный. Отменить Trust Calculus поля `F:`, `G:`, `R:`, `trust:`, `epistemic_stage:` как мёртвые. Семейство `family:` остаётся. При методизации Ф4 зафиксировать: поле `family:` = активный стандарт, Trust Calculus поля = официально deprecated.

**Действие:** при подготовке Ф4 добавить в «жизненный цикл кода» секцию отменённых кодов с датой.

## COL-05a: grep-аудит registry.json 🟢

**Суть.** Перед любым вердиктом по `registry.json` нужно установить факт: читает ли его что-то живое (Python-скрипты, хуки, CI).

**Действие (автономно, ~10 мин):** `grep -r "registry.json" ~/IWE/ --include="*.py" --include="*.sh" --include="*.yaml" -l`

**Предлагаемый вердикт.** Провести grep, занести результат в WP-419-registry-catalog-inventory.md §2. Никаких решений по файлу — только факт «читается / не читается».

## COL-05b: решение по registry.json (после grep-аудита) 🟡

**Суть.** `registry.json` описывает ядра (A/B/C/D) машиночитаемо, но рассинхронизирован с реальными именами папок и моделью ядер в документах.

**Счётчики.**
- Читателей `registry.json`: определяется в COL-05a
- Обновлений: давно не обновлялся (по инвентаризации)

**Предлагаемый вердикт.** Зависит от результата COL-05a:
- Никто не читает → кандидат на удаление (автономный вердикт).
- Читается → перегенерировать из реальной структуры + поставить под валидатор.

**Нужен пилот:** только если читается и нужно решение о перегенерации (второй ветке).

## COL-06: L0-L3 (инструкции агента vs уровни стиля) 🟡

**Суть.** В CLAUDE.md §7 L0/L1/L2/L3 = слои инструкций (L1=платформа, L2=staging, L3=авторское). В communication-style-base.md L0=базовый стиль, L1=авторский стиль. Одни обозначения, разные смыслы.

**Счётчики.**
- L0/L1/L2/L3 в текстах: ~52 файла. Смешение смыслов в документации вероятно.

**Предлагаемый вердикт.** Пространства имён с явным контекстом:
- «слои инструкций агента L1-L3» = термин CLAUDE.md
- «уровень стиля общения L0/L1» = термин DP.SC.050

Действие: при написании Ф4 добавить в метод: «при вводе нового кода указывать контекст (пространство имён) в документации». При необходимости переименовать стилевые уровни: L0-base / L1-author → убирает перекрытие.

**Нужен пилот:** для решения о переименовании уровней стиля.

## COL-07: P5 (инженерный стиль vs режим-отказа агента) 🟢

**Суть.** P5 в DP.SC.172 (инженерный стиль кода) = запах «длинная функция со смешанными обязанностями / булевы флаги-режимы». P5-block в правилах агента (AR.NNN) = режим-отказа на микро-вопросы. Разные пространства имён, низкий риск перепутать.

**Счётчики.**
- `P5` в текстах: ~8 файлов. Разные контексты явно различимы по теме.

**Предлагаемый вердикт.** Автономный. Не коллизия де-факто — контекст всегда разграничивает. При ссылке: `P5 (DP.SC.172)` или `P5-block (AR.NNN)`. Зафиксировать в методе Ф4 как пример «допустимого дублирования кодов при явном namespace».

---

## COL-08: R1 (роль Стратег vs мнемоника стиля «читатель-пилот») 🟢

**Суть.** R1 в roles.md / DP.ROLE.012 = Стратег. R1 как мнемоника в communication-style-base.md = «Читатель - пилот» (правило R1 авторского стиля). Разные пространства имён, практически не пересекаются в одном документе.

**Счётчики.**
- `R1` в текстах IWE: ~15 файлов. Смешение крайне маловероятно — тексты о стиле и тексты о ролях редко пересекаются.

**Предлагаемый вердикт.** Автономный. Аналогично COL-07: допустимое дублирование при явном namespace. При ссылке: `R1 (роль Стратег)` или `R1 (стиль A4-A8)`. Зафиксировать в методе Ф4.
