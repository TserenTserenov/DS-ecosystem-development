# WP-468 — Воспроизводимая среда разработки

## Коротко

РП-468 устраняет ситуацию, когда каждый разработчик вручную собирает окружение и получает свой набор версий программ и зависимостей. Вместо инструкции «установите примерно такие инструменты» репозиторий сам хранит точное описание среды разработки.

Предлагается не создавать одно тяжёлое окружение на весь мультирепозиторий IWE, а хранить конфигурацию рядом с кодом каждого сервиса, которому она действительно нужна:

- `gateway-mcp` — Nix devShell с закреплённым Node.js 22;
- `aist_bot` — уже существующий DevContainer/Docker с Python 3.11.

Ожидаемый результат: разработчик клонирует репозиторий, запускает стандартные команды и получает ту же среду, что коллега и сервер. Доступ к продакшену из этой среды автоматически не выдаётся.

## Какую проблему решаем

### 1. «У меня работает» не означает «работает у команды»

Сейчас результат может зависеть от того, что уже установлено на конкретном компьютере:

- версия Node.js или Python;
- версия npm и разрешённое им дерево зависимостей;
- системные библиотеки;
- случайно оставшийся `node_modules` или виртуальное окружение;
- локальные переменные окружения, о которых не сказано в инструкции.

Из-за этого один разработчик видит успешный запуск, а другой — ошибку. Сервер может получить третье поведение.

### 2. Подключение нового разработчика требует ручной настройки

Новому участнику приходится выяснять:

- какие версии инструментов нужны;
- откуда брать зависимости;
- какие команды считаются правильными;
- какие секреты действительно нужны, а какие не должны выдаваться;
- как понять, что окружение собрано правильно.

Это увеличивает время входа и создаёт скрытые знания, которые находятся у отдельных людей, а не в репозитории.

### 3. Локальная разработка расходится с сервером

Если разработчик использует один набор версий, а сервер — другой, дефекты обнаруживаются поздно. РП-468 переносит описание инструментов в Git, чтобы изменения среды проходили обычное ревью вместе с кодом.

## Что предлагается

### Принцип: конфигурация принадлежит сервису

У каждого сервиса собственный минимальный способ воспроизведения среды:

| Репозиторий | Механизм | Что закрепляет | Нужны ли секреты для базовой проверки |
|---|---|---|---|
| [`aisystant/gateway-mcp`](https://github.com/aisystant/gateway-mcp) | Nix flake + опциональный direnv | Node.js 22 и системное окружение | Нет |
| [`aisystant/aist_bot`, ветка `new-architecture`](https://github.com/aisystant/aist_bot/tree/new-architecture) | DevContainer + Docker Compose | Python 3.11, системные и Python-зависимости | Для сборки — нет; для запуска бота — да |

Один общий flake на корень IWE не предлагается: IWE состоит из разных репозиториев и языков, а большинству документов и Packs собственный runtime не нужен.

### Референс

Исходный пример — ветка [`python-gcp` репозитория knowledge-mcp](https://github.com/aisystant/knowledge-mcp/tree/python-gcp). В ней используется Nix flake + devenv + direnv. Для `gateway-mcp` взята более простая часть этого подхода: обычный Nix devShell без devenv, потому что в dev-среде Gateway не нужно поднимать отдельную базу или управляемый локальный сервис.

## Что уже реализовано

### `gateway-mcp`

Подготовлены четыре файла:

- `flake.nix` — описание Node.js 22 и поддерживаемых платформ;
- `flake.lock` — точная версия Nixpkgs;
- `.envrc` — автоматический вход через direnv командой `use flake`;
- `package-lock.json` — синхронизирован с `package.json`, чтобы работал чистый `npm ci`.

Поддерживаются:

- Apple Silicon: `aarch64-darwin`;
- Intel Mac: `x86_64-darwin`;
- ARM Linux: `aarch64-linux`;
- обычный 64-битный Linux: `x86_64-linux`.

Проверено 5 августа 2026 года:

- Nix devShell выдаёт Node.js 22.23.2;
- `npm ci --ignore-scripts` проходит на чистом дереве;
- проверка типов проходит;
- 20 тестовых файлов и 206 тестов проходят локально;
- те же команды прошли во временном чистом каталоге на сервере `tsekh-1` (`x86_64-linux`, Nix 2.28.5);
- Hermes Agent независимо проверил изменение lock-файла и подтвердил решение.

Изменения Gateway пока находятся в локальных коммитах. Перед проверкой коллегой их нужно опубликовать в отдельной небоевой ветке или передать архивом. Слияние в `main` выполняется отдельно, потому что в Gateway оно запускает боевое развёртывание.

### `aist_bot`

Новая конфигурация не создавалась: в ветке `new-architecture` уже есть:

- [`.devcontainer/devcontainer.json`](https://github.com/aisystant/aist_bot/blob/new-architecture/.devcontainer/devcontainer.json);
- [`docker-compose.yml`](https://github.com/aisystant/aist_bot/blob/new-architecture/docker-compose.yml);
- [`Dockerfile`](https://github.com/aisystant/aist_bot/blob/new-architecture/Dockerfile);
- [`.env.example`](https://github.com/aisystant/aist_bot/blob/new-architecture/.env.example).

Образ локально собран, безопасный запуск подтвердил Python 3.11.15. Полный запуск бота не выполнялся, потому что локального `.env` нет, а выдумывать или копировать производственные секреты ради теста нельзя.

## Как всё будет работать после внедрения

### Обычный рабочий день разработчика Gateway

```text
Клонировать репозиторий
        ↓
Войти в Nix-среду
        ↓
Установить точные зависимости через npm ci
        ↓
Запустить проверку типов и тесты
        ↓
Разрабатывать внутри той же среды
        ↓
Передать изменение в ревью
```

Разработчик не выбирает версию Node.js вручную. Версия берётся из `flake.lock`. Зависимости берутся из `package-lock.json`. Изменение версий происходит отдельным коммитом и проверяется командой.

### Обновление среды

Если нужна новая версия Node.js или Nixpkgs:

1. Ответственный разработчик меняет `flake.nix` или обновляет `flake.lock`.
2. Выполняет чистую установку, проверку типов и тесты.
3. Открывает pull request с объяснением изменения среды.
4. После ревью команда сливает изменение.
5. Остальные разработчики выполняют `git pull`; Nix автоматически получает новую закреплённую версию.

Никому не нужно отдельно рассылать инструкцию «обновите Node.js до такой-то версии».

### Связь с CI и сервером

Следующий шаг после приёмки пилота — перевести CI Gateway на те же команды `nix develop -c ...`. Тогда локальная проверка, проверка pull request и серверная проверка используют одну декларацию среды.

Это не означает автоматического доступа к серверу или автоматического развёртывания. Развёртывание остаётся отдельным процессом с отдельными правами.

## Кто что должен сделать

### 1. Владелец Gateway или ведущий разработчик

**Цель:** безопасно передать текущую реализацию на независимую проверку.

1. Открыть [`aisystant/gateway-mcp`](https://github.com/aisystant/gateway-mcp).
2. Опубликовать два подготовленных коммита в отдельную небоевую ветку или передать коллеге Git-архив.
3. Не сливать их в `main` на этом шаге: `main` запускает боевое развёртывание.
4. Дать коллеге ссылку на конкретную ветку или commit.
5. После результата коллеги открыть pull request в `main`.
6. Перед слиянием убедиться, что изменения ограничены `.envrc`, `flake.nix`, `flake.lock` и `package-lock.json`.
7. Отдельно согласовать с пилотом слияние, поскольку оно запускает развёртывание Gateway.

### 2. Независимый разработчик команды

**Кто подходит:** любой разработчик, который не участвовал в настройке и работает на другом компьютере. Доступ к продакшену не нужен. Достаточно чтения репозитория или полученного архива.

#### Подготовка

1. Установить Git.
2. Установить Nix по [официальной инструкции](https://nixos.org/download/).
3. Опционально установить direnv по [инструкции официального репозитория](https://github.com/direnv/direnv/blob/master/docs/installation.md). Для проверки он не обязателен.
4. Получить от владельца Gateway ссылку на проверяемую ветку или commit.

#### Чистая проверка

```bash
git clone https://github.com/aisystant/gateway-mcp.git
cd gateway-mcp
git switch <ветка, которую сообщил владелец Gateway>

nix develop -c node --version
nix develop -c npm ci --ignore-scripts
nix develop -c npm run typecheck
nix develop -c npm test
```

Если используется direnv:

```bash
direnv allow
node --version
npm ci --ignore-scripts
npm run typecheck
npm test
```

#### Что считать успехом

- вывод Node.js начинается с `v22`;
- `npm ci --ignore-scripts` завершается без ручной установки пакетов;
- проверка типов завершается успешно;
- проходят 20 тестовых файлов и 206 тестов;
- не понадобились `.env`, токены, SSH или доступ к Cloudflare;
- не понадобилось менять `flake.nix`, `package.json` или lock-файлы.

#### Что вернуть владельцу Gateway

```text
ОС и версия:
Архитектура: aarch64 или x86_64
Версия Nix:
Версия Node.js внутри nix develop:
npm ci: успешно / ошибка
typecheck: успешно / ошибка
tests: число файлов и тестов
Дополнительные ручные действия: не было / перечислить
```

Если команда падает, коллега не должен чинить окружение вручную. Нужно прислать команду и полный текст ошибки: именно отсутствие скрытых ручных действий является предметом проверки.

### 3. Владелец `aist_bot` или уполномоченный разработчик

**Цель:** проверить существующий DevContainer без выдачи лишних прав и без воздействия на реального бота.

#### Что установить

- [Docker Desktop](https://docs.docker.com/desktop/);
- VS Code;
- расширение и документацию [Dev Containers](https://code.visualstudio.com/docs/devcontainers/containers).

#### Безопасная проверка сборки без секретов

```bash
git clone https://github.com/aisystant/aist_bot.git
cd aist_bot
git switch new-architecture
docker build -t aist-bot-dev-check .
docker run --rm --entrypoint python aist-bot-dev-check --version
docker image rm aist-bot-dev-check
```

Ожидается Python 3.11. Эта проверка не запускает Telegram-бота и не требует `.env`. Последняя команда удаляет только локальный проверочный образ; при необходимости он полностью восстанавливается повторной сборкой.

#### Полный запуск DevContainer

1. Скопировать список переменных:

   ```bash
   cp .env.example .env
   ```

2. Получить **тестовые**, а не производственные значения у владельцев соответствующих сервисов. GitHub содержит только имена переменных в `.env.example`; реальные секреты из GitHub брать нельзя.
3. Если место хранения тестовых секретов не определено, остановиться и сообщить пилоту. Текущее РП не фиксирует единый секретный сейф, поэтому придумывать источник нельзя.
4. Проверить конфигурацию:

   ```bash
   docker compose config --quiet
   ```

5. Открыть папку в VS Code и выбрать `Dev Containers: Reopen in Container`.
6. Полный запуск разрешён только с изолированными тестовыми Telegram-токеном и базами. Производственные токены могут отправить реальные сообщения или изменить данные.
7. После проверки остановить контейнеры:

   ```bash
   docker compose down
   ```

Файл `.env` не коммитить и не пересылать в отчёте.

### 4. Пилот или технический руководитель

1. Назначить независимого разработчика для проверки Gateway.
2. Решить, кто является владельцем тестовых секретов `aist_bot`.
3. Убедиться, что для полного запуска бота выданы тестовые, а не производственные значения.
4. Принять результат проверки коллеги.
5. Отдельно разрешить или отклонить слияние Gateway в `main` с боевым развёртыванием.
6. После всех подтверждений закрыть Ф3 и РП-468.

## Какие права нужны и что разработчик может поломать

### Для проверки Gateway

Достаточно чтения кода. Не нужны:

- право записи в `main`;
- Cloudflare;
- Railway;
- SSH на сервер;
- производственные базы;
- токены и `.env`;
- доступ ко всему рабочему дереву IWE.

`npm ci` удаляет и пересоздаёт только `node_modules` в чистом клоне коллеги. `nix develop` добавляет инструменты в Nix store. Поэтому при отсутствии внешних ключей коллега может повредить только свою временную копию — её можно удалить и клонировать заново.

### Для проверки `aist_bot`

Сборка образа безопасна без секретов. Запуск бота с реальными токенами уже может воздействовать на Telegram и базы, поэтому его выполняет только уполномоченный владелец с тестовой конфигурацией.

## Известные ограничения и отдельные задачи

1. `npm audit` для Gateway сообщает 12 известных уязвимостей, включая 6 в производственном дереве. Автоматический `npm audit fix` не запускался: обновление рабочих зависимостей требует отдельной оценки совместимости по связке WP-212.
2. Единый документированный источник тестовых секретов `aist_bot` не найден. До его определения полный запуск нельзя передавать случайному разработчику.
3. CI ещё не переведён на `nix develop`; это следующий шаг после независимой приёмки.
4. Конфигурация не выдаёт права на продакшен и не заменяет процесс развёртывания.
5. Nixpkgs 26.05 — последний выпуск с поддержкой Intel Mac (`x86_64-darwin`). При следующем обновлении Nixpkgs нужно отдельно решить, сохраняет ли команда поддержку таких компьютеров.
