# WP-468 — Подключение разработчиков к новой платформе и IWE

<details>
<summary><strong>Коротко</strong></summary>

Главная задача РП-468 — создать понятный и безопасный маршрут подключения нового разработчика к новой платформе Aisystant и рабочему контуру IWE. Новый коллега должен без устной передачи скрытых знаний понять:

- с какого документа и репозитория начинать;
- какой минимальный доступ ему нужен;
- как подготовить рабочее место;
- как проверить готовность до получения первой задачи;
- к кому обращаться, если проверка не проходит;
- какие дополнительные права выдаются только под конкретную задачу.

Воспроизводимая среда разработки — не самоцель, а техническая часть этого маршрута. Она убирает ручную настройку и позволяет проверить готовность разработчика без доступа к производственным системам:

- `gateway-mcp` — Nix devShell с закреплённым Node.js 22;
- `aist_bot` — уже существующий DevContainer/Docker с Python 3.11.

Ожидаемый результат: новый разработчик получает ровно необходимые репозитории, проходит одну документированную проверку и подтверждает, что готов к первой безопасной задаче. Доступ к продакшену, боевым секретам и всему IWE автоматически не выдаётся.

</details>

<details>
<summary><strong>Какую проблему решаем</strong></summary>

### 1. Нет единого технического входа для нового разработчика

Новый коллега видит много репозиториев, документов и сервисов, но не получает одного маршрута от приглашения до первой задачи. Ему приходится отдельно выяснять:

- где находится контекст IWE и описание новой платформы;
- какой сервис брать первым;
- кто владеет сервисом и принимает результат;
- какая команда доказывает, что рабочее место готово;
- что делать при ошибке и кому её передавать.

Без такого входа подключение зависит от времени и памяти конкретного участника команды.

### 2. Не определена безопасная граница доступа

Если заранее не разделить базовый и рабочий доступ, возникают две крайности: разработчик либо ждёт лишних согласований, либо получает больше прав, чем требуется для первой задачи. Для входной проверки не нужны:

- запись в `main`;
- доступ к производственным базам и серверам;
- Cloudflare, Railway и боевые токены;
- полная копия всех рабочих репозиториев IWE.

Дополнительные права должны появляться только после выбора первой задачи и подтверждения владельца соответствующего сервиса.

### 3. Рабочее место собирается по устным инструкциям

Даже после выдачи доступа новый разработчик вручную подбирает версии Node.js или Python, зависимости и команды. Это растягивает подключение и создаёт скрытые знания вне Git.

### 4. «У меня работает» — следствие, а не главная проблема

Разные локальные версии приводят к тому, что код работает у одного участника, но не у другого или на сервере. РП-468 устраняет этот риск как часть подключения: описание инструментов хранится рядом с кодом и проходит ревью вместе с ним.

</details>

<details>
<summary><strong>Что предлагается</strong></summary>

### Единый маршрут подключения

| Этап | Что происходит | Результат |
|---|---|---|
| 1. Назначение | Пилот назначает владельца подключения и первый учебный или рабочий сервис | Понятно, кто отвечает за вход и принимает проверку |
| 2. Контекст IWE | Разработчик получает этот документ, карточку РП и только нужные ему материалы новой платформы | Понятны цель, границы и расположение рабочих материалов |
| 3. Минимальный доступ | Владелец выдаёт чтение целевого репозитория; запись и производственные права не выдаются | Можно начать без риска для работающей системы |
| 4. Подготовка | Разработчик устанавливает Git и один поддерживаемый механизм среды — Nix либо Docker/DevContainer | Компьютер готов получить среду из репозитория |
| 5. Самопроверка | Разработчик клонирует репозиторий и выполняет команды из этого документа | Получено проверяемое доказательство готовности |
| 6. Приёмка | Владелец проверяет результат и фиксирует недостающие ручные действия | Понятно, готов ли маршрут для следующего новичка |
| 7. Первая задача | Только после приёмки выдаются права и тестовые секреты, необходимые для конкретной задачи | Разработчик начинает работу с минимально необходимыми полномочиями |

Технический пилот маршрута выполняется на двух сервисах: `gateway-mcp` показывает вход в TypeScript-сервис через Nix, а `aist_bot` — вход в Python-сервис через DevContainer. После независимой приёмки тот же шаблон можно применять к другим сервисам платформы.

### Принцип: конфигурация принадлежит сервису

У каждого сервиса собственный минимальный способ воспроизведения среды:

| Репозиторий | Механизм | Что закрепляет | Нужны ли секреты для базовой проверки |
|---|---|---|---|
| [`aisystant/gateway-mcp`](https://github.com/aisystant/gateway-mcp) | Nix flake + опциональный direnv | Node.js 22 и системное окружение | Нет |
| [`aisystant/aist_bot`, ветка `new-architecture`](https://github.com/aisystant/aist_bot/tree/new-architecture) | DevContainer + Docker Compose | Python 3.11, системные и Python-зависимости | Для сборки — нет; для запуска бота — да |

Один общий flake на корень IWE не предлагается: IWE даёт разработчику рабочий контекст и правила, а каждый программный сервис хранит собственную исполняемую среду. Так подключение остаётся единым по логике, но не заставляет все репозитории использовать один язык или набор инструментов.

### Референс

Исходный пример — ветка [`python-gcp` репозитория knowledge-mcp](https://github.com/aisystant/knowledge-mcp/tree/python-gcp). В ней используется Nix flake + devenv + direnv. Для `gateway-mcp` взята более простая часть этого подхода: обычный Nix devShell без devenv, потому что в dev-среде Gateway не нужно поднимать отдельную базу или управляемый локальный сервис.

</details>

### `gateway-mcp`

Подготовлены четыре файла:

- `flake.nix` — описание Node.js 22 и поддерживаемых платформ;
- `flake.lock` — точная версия Nixpkgs;
- `.envrc` — автоматический вход через direnv командой `use flake`;
- `package-lock.json` — синхронизирован с `package.json`, чтобы работал чистый `npm ci`.

Поддерживаются:

- Apple Silicon: `aarch64-darwin`;
- Intel Mac: `x86_64-darwin`;
- ARM Linux: `aarch64-linux`;
- обычный 64-битный Linux: `x86_64-linux`.

Проверено 5 августа 2026 года:

- Nix devShell выдаёт Node.js 22.23.2;
- `npm ci --ignore-scripts` проходит на чистом дереве;
- проверка типов проходит;
- 20 тестовых файлов и 206 тестов проходят локально;
- те же команды прошли во временном чистом каталоге на сервере `tsekh-1` (`x86_64-linux`, Nix 2.28.5);
- Hermes Agent независимо проверил изменение lock-файла и подтвердил решение.

Изменения Gateway уже опубликованы в `main`: Nix-среда — commit `21df453`, синхронизация `package-lock.json` — commit `e2d9d26`. Новый разработчик может выполнять проверку сразу на текущей основной ветке. Само слияние уже выполнено и запустило штатный процесс развёртывания; для входной проверки никакого повторного развёртывания не требуется.

<details>
<summary><strong>Как всё будет работать в будущем</strong></summary>

### Подключение нового разработчика

```text
Пилот назначает владельца подключения и первый сервис
        ↓
Владелец передаёт контекст IWE и выдаёт чтение репозитория
        ↓
Разработчик разворачивает среду по инструкции из репозитория
        ↓
Автоматическая проверка подтверждает версии, зависимости и тесты
        ↓
Владелец принимает результат или получает полный текст ошибки
        ↓
Разработчик получает первую задачу и только необходимые для неё права
```

Вход завершается не фактом «репозиторий открылся», а наблюдаемым результатом: чистая копия собирается, стандартные проверки проходят, скрытые ручные действия не потребовались, владелец сервиса подтвердил готовность.

### Обычный рабочий день разработчика Gateway

```text
Клонировать репозиторий
        ↓
Войти в Nix-среду
        ↓
Установить точные зависимости через npm ci
        ↓
Запустить проверку типов и тесты
        ↓
Разрабатывать внутри той же среды
        ↓
Передать изменение в ревью
```

Разработчик не выбирает версию Node.js вручную. Версия берётся из `flake.lock`. Зависимости берутся из `package-lock.json`. Изменение версий происходит отдельным коммитом и проверяется командой.

### Обновление среды

Если нужна новая версия Node.js или Nixpkgs:

1. Ответственный разработчик меняет `flake.nix` или обновляет `flake.lock`.
2. Выполняет чистую установку, проверку типов и тесты.
3. Открывает pull request с объяснением изменения среды.
4. После ревью команда сливает изменение.
5. Остальные разработчики выполняют `git pull`; Nix автоматически получает новую закреплённую версию.

Никому не нужно отдельно рассылать инструкцию «обновите Node.js до такой-то версии».

### Связь с CI и сервером

Следующий шаг после приёмки пилота — перевести CI Gateway на те же команды `nix develop -c ...`. Тогда локальная проверка, проверка pull request и серверная проверка используют одну декларацию среды.

Это не означает автоматического доступа к серверу или автоматического развёртывания. Развёртывание остаётся отдельным процессом с отдельными правами.

<summary><strong>Кто что должен сделать</strong></summary>

### 1. Владелец Gateway или ведущий разработчик

**Цель:** провести нового разработчика от выдачи минимального доступа до подтверждённой готовности к первой задаче.

1. Открыть [`aisystant/gateway-mcp`](https://github.com/aisystant/gateway-mcp).
2. Если репозиторий закрытый, выдать коллеге право чтения без записи в `main` и без производственных доступов.
3. Передать ссылку на этот документ и сообщить, что проверяется текущая ветка `main`.
4. Попросить выполнить чистую проверку ниже на другом компьютере.
5. Принять заполненный результат или полный текст ошибки.
6. Не предлагать ручные обходы: каждое недостающее действие нужно добавить в репозиторий или инструкцию отдельным изменением через pull request.
7. После успешной приёмки назначить первую задачу и отдельно согласовать только те дополнительные права, которые для неё действительно нужны.

### 2. Независимый разработчик команды

**Кто подходит:** любой разработчик, который не участвовал в настройке и работает на другом компьютере. Доступ к продакшену не нужен. Достаточно чтения репозитория или полученного архива.

#### Подготовка

1. Установить Git.
2. Установить Nix по [официальной инструкции](https://nixos.org/download/).
3. Опционально установить direnv по [инструкции официального репозитория](https://github.com/direnv/direnv/blob/master/docs/installation.md). Для проверки он не обязателен.
4. Получить от владельца Gateway право чтения репозитория и ссылку на этот документ.

#### Чистая проверка

```bash
git clone https://github.com/aisystant/gateway-mcp.git
cd gateway-mcp

nix develop -c node --version
nix develop -c npm ci --ignore-scripts
nix develop -c npm run typecheck
nix develop -c npm test
```

Если используется direnv:

```bash
direnv allow
node --version
npm ci --ignore-scripts
npm run typecheck
npm test
```

#### Что считать успехом

- вывод Node.js начинается с `v22`;
- `npm ci --ignore-scripts` завершается без ручной установки пакетов;
- проверка типов завершается успешно;
- проходят 20 тестовых файлов и 206 тестов;
- не понадобились `.env`, токены, SSH или доступ к Cloudflare;
- не понадобилось менять `flake.nix`, `package.json` или lock-файлы.

#### Что вернуть владельцу Gateway

```text
ОС и версия:
Архитектура: aarch64 или x86_64
Версия Nix:
Версия Node.js внутри nix develop:
npm ci: успешно / ошибка
typecheck: успешно / ошибка
tests: число файлов и тестов
Дополнительные ручные действия: не было / перечислить
```

Если команда падает, коллега не должен чинить окружение вручную. Нужно прислать команду и полный текст ошибки: именно отсутствие скрытых ручных действий является предметом проверки.

### 3. Владелец `aist_bot` или уполномоченный разработчик

**Цель:** проверить существующий DevContainer без выдачи лишних прав и без воздействия на реального бота.

#### Что установить

- [Docker Desktop](https://docs.docker.com/desktop/);
- VS Code;
- расширение и документацию [Dev Containers](https://code.visualstudio.com/docs/devcontainers/containers).

#### Безопасная проверка сборки без секретов

```bash
git clone https://github.com/aisystant/aist_bot.git
cd aist_bot
git switch new-architecture
docker build -t aist-bot-dev-check .
docker run --rm --entrypoint python aist-bot-dev-check --version
docker image rm aist-bot-dev-check
```

Ожидается Python 3.11. Эта проверка не запускает Telegram-бота и не требует `.env`. Последняя команда удаляет только локальный проверочный образ; при необходимости он полностью восстанавливается повторной сборкой.

#### Полный запуск DevContainer

1. Скопировать список переменных:

   ```bash
   cp .env.example .env
   ```

2. Получить **тестовые**, а не производственные значения у владельцев соответствующих сервисов. GitHub содержит только имена переменных в `.env.example`; реальные секреты из GitHub брать нельзя.
3. Если место хранения тестовых секретов не определено, остановиться и сообщить пилоту. Текущее РП не фиксирует единый секретный сейф, поэтому придумывать источник нельзя.
4. Проверить конфигурацию:

   ```bash
   docker compose config --quiet
   ```

5. Открыть папку в VS Code и выбрать `Dev Containers: Reopen in Container`.
6. Полный запуск разрешён только с изолированными тестовыми Telegram-токеном и базами. Производственные токены могут отправить реальные сообщения или изменить данные.
7. После проверки остановить контейнеры:

   ```bash
   docker compose down
   ```

Файл `.env` не коммитить и не пересылать в отчёте.

### 4. Пилот или технический руководитель

1. Назначить одного владельца подключения и независимого разработчика для сквозной проверки маршрута.
2. Выбрать первый сервис: Gateway для безопасной проверки без секретов, `aist_bot` — только если нужен Python-контур.
3. Убедиться, что новый разработчик получил контекст IWE и чтение только необходимых репозиториев.
4. Решить, кто является владельцем тестовых секретов `aist_bot`.
5. Убедиться, что для полного запуска бота выданы тестовые, а не производственные значения.
6. Принять результат независимого прохода от приглашения до успешной проверки.
7. После всех подтверждений закрыть Ф3 и РП-468.

<details>
<summary><strong>Какие права нужны и что разработчик может поломать</strong></summary>

### Базовый доступ при подключении

На первом этапе разработчик получает чтение этого документа, карточки РП и целевого репозитория. Этого достаточно, чтобы понять устройство входного задания и проверить рабочее место. Доступ к другим частям IWE и платформы выдаётся по мере появления конкретных задач, а не заранее «на всякий случай».

### Для проверки Gateway

Достаточно чтения кода. Не нужны:

- право записи в `main`;
- Cloudflare;
- Railway;
- SSH на сервер;
- производственные базы;
- токены и `.env`;
- доступ ко всему рабочему дереву IWE.

`npm ci` удаляет и пересоздаёт только `node_modules` в чистом клоне коллеги. `nix develop` добавляет инструменты в Nix store. Поэтому при отсутствии внешних ключей коллега может повредить только свою временную копию — её можно удалить и клонировать заново.

### Для проверки `aist_bot`

Сборка образа безопасна без секретов. Запуск бота с реальными токенами уже может воздействовать на Telegram и базы, поэтому его выполняет только уполномоченный владелец с тестовой конфигурацией.

</details>

4. Конфигурация не выдаёт права на продакшен и не заменяет процесс развёртывания.
5. Nixpkgs 26.05 — последний выпуск с поддержкой Intel Mac (`x86_64-darwin`). При следующем обновлении Nixpkgs нужно отдельно решить, сохраняет ли команда поддержку таких компьютеров.
6. Полный сквозной проход подключения новым независимым разработчиком ещё не выполнен. До этого РП-468 нельзя считать окончательно принятым только на основании проверок автора.
