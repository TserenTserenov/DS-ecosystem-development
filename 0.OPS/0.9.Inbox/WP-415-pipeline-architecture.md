## Три конвейера синхронизации

### 🔄 Конвейер 1: Личный RU ↔ aisystant приватные RU

**Назначение:** синхронизация личного черновика шаблона с рабочей площадкой команды в `aisystant`.

**Участники:**
- Источник: личный репо `TserenTserenov/FMT-exocortex-template` (RU)
- Приёмник: семейство приватных RU-репо в `aisystant` (один или несколько)
- Актор: GitHub App `canon-sync` (owner = пилот)

**Поток:**

```
[Личный RU-шаблон (TserenTserenov/FMT-...)]
  ↓ git push (пилот пишет обновления)
  
[webhook → GitHub Actions]
  
[aisystant/docs-aisystant (приватный RU-источник)]
  ↓ (команда может редактировать здесь же)
```

**Вопрос архитектуры:** однонаправленно (личный → aisystant) или двусторонне?
- **Вариант A (pull-only):** `aisystant` получает обновления из личного, команда читает и комментирует, но не редактирует сам источник
- **Вариант B (push-only):** пилот пишет, синкает в `aisystant`, команда берёт оттуда
- **Вариант C (двусторонний):** оба репо остаются в синхронизации, команда может редактировать приватный `aisystant`, обновления перетекают обратно в личный

**Решение пилота нужно:**
- Выбрать вариант (A/B/C)
- Если B или C — определить механику (git hooks, Actions, ручное слияние)

### 🌍 Конвейер 2: aisystant приватные RU → iwesys публичные EN

**Назначение:** автоматический перевод русскоязычного контента на английский для мировой аудитории в организации `iwesys`.

**Участники:**
- Источник: приватные RU-репо в `aisystant` (docs-ru, guides-ru, и т.д.)
- Приёмник: публичные EN-репо в `iwesys` (docs-en, guides-en, и т.д.)
- Актор: GitHub App `canon-sync` (owner = пилот)
- Трансформер: `translate.py` + `enrich-glossary.py` (из FMT-exocortex-template)

**Поток:**

```
[aisystant/docs-ru (приватный RU)]
  ↓ git push (автор пишет/редактирует)
  
[webhook → GitHub Actions (aisystant)]
  ↓ Запускается скрипт translate.py:
    ├─ Дельта-перевод (только изменившееся)
    ├─ Проверка глоссария (важные термины обязаны быть переведены)
    ├─ Проверка целостности (нет ли обрезки контента)
    └─ Форматирование EN-стиля

[iwesys/docs-en (публичный EN)]
  ↓ (результат пушится автоматически)
```

**Статус:** ✅ **READY TO DEPLOY** (В2 done, В2.5 done, В2.6 done 06.07)
- Код написан и залит в FMT-exocortex-template
- Глоссарий синхронизирован (96-126 терминов, Tier-1/2/3)
- 3 дефекта найдены и закрыты на живом прогоне (потеря данных + утечка меток + обрезка)
- GitHub App `canon-sync` установлен в `aisystant`

**Что нужно для запуска:**
1. Убедиться, что `iwesys` уже создан и доступен приложению (проверка разрешений)
2. Создать целевые EN-репо в `iwesys` (пустые) — `docs-en`, `guides-en`, и т.д.
3. Дать GitHub App разрешение на запись в `iwesys`
4. Сделать контрольный пуш в `aisystant/docs-ru` → проверить результат в `iwesys/docs-en`

### 🇷🇺 Конвейер 3: aisystant приватные RU → mimsys публичные RU

**Назначение:** синхронизация русскоязычного контента в публичную организацию `mimsys` (для России, для читателей).

**Участники:**
- Источник: приватные RU-репо в `aisystant` (docs-ru, guides-ru и т.д.)
- Приёмник: публичные RU-репо в `mimsys` (docs-ru, guides-ru и т.д.)
- Актор: GitHub App `canon-sync` (owner = пилот)
- Трансформер: прямая копия (без перевода), только проверка формата

**Поток:**

```
[aisystant/docs-ru (приватный RU)]
  ↓ git push (автор пишет/редактирует)
  
[webhook → GitHub Actions (aisystant)]
  ↓ Запускается скрипт copy-to-mimsys.py:
    ├─ Копирование контента как есть (RU текст не меняется)
    ├─ Проверка целостности формата
    └─ Проверка, что нет секретов/приватных данных

[mimsys/docs-ru (публичный RU)]
  ↓ (результат пушится автоматически)
```

**Статус:** ⏳ **ДИЗАЙН В РАБОТЕ** (Фаза В7)
- Архитектура принята на встрече 05.07
- GitHub App `canon-sync` установлен в `mimsys`
- Спека через IntegrationGate требуется (обещание → сценарии → роль → код)

**Что нужно:**
1. **Спека В7:** интеграционный гейт (документ с 4 секциями)
   - Обещание: что гарантирует конвейер (не потеря данных, не утечка секретов)
   - Сценарии: типичные пути использования (автор пишет → публикуется в МИМ)
   - Роль: кто отвечает за конвейер (GitHub App собственник, алёрт на неудачу)
   - Реализация: код скрипта copy-to-mimsys.py
2. **Тест на smoke:** пуш в aisystant/docs-ru → проверка, что появилось в mimsys/docs-ru
3. **Алёрт на отказ:** если конвейер упал, должен быть сигнал (webhook, Telegram)

**Вопрос архитектуры:** может ли быть коллизия между конвейером 2 (перевод) и конвейером 3 (копирование)?
- **Нет**, если механика правильная. Конвейер 2 пушит в `iwesys`, конвейер 3 в `mimsys` — разные целевые организации
- Оба триггеры на push в один источник (`aisystant/docs-ru`) — это OK, можно настроить GitHub Actions на параллельный запуск двух скриптов

## Гарантии конвейеров

### Конвейер 2 (RU → EN) гарантирует:

✅ **На основе В2.6 (живой прогон 06.07):**
- Дельта-перевод (переводит только изменения)
- Целостность файлов (нет потери данных, нет обрезки больших документов)
- Чистый EN-формат (нет утечки служебных меток, нет кириллицы в коде)
- Глоссарий (96-126 терминов, уровни важности, регрессионные тесты)
- Бейдж статуса в README (✅ PASS / ⚠️ WARNING / ❌ FAIL)

❌ **НЕ гарантирует:**
- Идеальное качество перевода (Haiku-модель, не Opus)
- Контекстные аспекты (иногда нужна ручная доработка)
- Консистентность со старыми версиями (перевод дельта, база не обновляется)

### Конвейер 3 (RU → RU зеркало) гарантирует:

✅ **Когда спека готова:**
- Полная копия контента (как есть, без изменений)
- Отсутствие секретов (проверка паттернов токенов/ключей)
- Целостность (нет потери файлов)

❌ **НЕ гарантирует:**
- Полное отсутствие следов связи `aisystant` ↔ `mimsys` (GitHub кэши, временные метаданные)
- Приватность на уровне git-истории (история коммитов видна в обоих репо)
