# Доступ агентов к личной памяти пилота: архитектурное предложение

> **Источник:** пункты 3–6 оперативки ИТ 24 мая (приватность памяти, MCP-память, операторский MCP, дерево/граф).
> **Метод:** peer-сессия Claude + Kimi (4 хода, консенсус), результат — 4 кирпича + порядок пилота.
> **Цель документа:** согласовать с архитектором до начала реализации.

---

## 1. Проблема

Сейчас агент при работе получает доступ ко всему, что есть у пилота, и может делать что угодно. Нет разграничения:
- какому агенту можно читать какие домены личного хранилища
- кто может оставлять записи, а кто — только читать
- какие действия необратимы и требуют явного подтверждения

---

## 2. Четыре кирпича (предложение)

### Кирпич 1 — Дворецкий (MCP-слой памяти)

**Суть:** весь доступ агентов к личному хранилищу пилота только через единый посредник (MCP-сервер памяти). Агент не обращается к хранилищу напрямую. Посредник знает структуру хранилища, выдаёт ровно то, что разрешено.

**Связь с существующим:** Local Gateway (DP.IWE.005) уже делает нечто похожее для координации агентов в VS Code (file-lock между peer-агентами). Дворецкий памяти — расширение этой идеи на **доступ к знаниям**, а не только к файлам.

**Открытые вопросы для архитектора:**
- Дворецкий = расширение Local Gateway или отдельный сервис?
- Upstream-proxy к Aisystant MCP (запланировано в DP.IWE.005 §TODO) — это оно?
- Как дворецкий соотносится с Диспетчером, который открывает сессию?

---

### Кирпич 2 — Структура памяти (рабочий стол)

**Суть:** личное хранилище структурировано как рабочий стол. Ящики (домены: финансы, здоровье, работа, обучение, проекты) → стопки (проекты/темы) → листы с ярлыками (для поиска). Плюс уровни прозрачности внутри каждого листа: часть листа — только пилоту, часть — можно показать тренеру.

**Ключевая идея:** запись "поход к зубному" не единым документом, а тремя карточками: общая, диагноз, оплата — каждая с разным уровнем доступа. Ярлыки = для поиска, не для управления доступом. Доступ = по ящикам + уровням прозрачности.

**Связь с существующим:** Pack-personal (Git, ~10%) хранит часть этого. Neon Память.Derived (~85%) — агрегаты activity_log. Нужна ли единая структура поверх обоих?

**Открытые вопросы для архитектора:**
- Где физически живут "ящики" — в Pack-personal (Git), в Neon, или новый слой?
- Нужна ли новая таблица в Neon для этой структуры?
- Как это соотносится с Герmes memory (WP-316)?

---

### Кирпич 3 — Допуски по должностям

**Суть:** каждому агенту заранее выдаётся список доменов (ящиков), к которым он имеет доступ, + уровень доступа: посмотреть / оставить отметку / подписать от имени пилота. Без ожидания явного подтверждения для стандартного доступа (иначе агент стоит пока пилот спит). "Подписать от имени" — отдельная "доверенность", выдаётся не вместе с допуском.

**Связь с существующим:** Local Gateway §TODO "tool-allowlist per agent" — похожая идея, но для инструментов, а не для доменов памяти.

**Открытые вопросы для архитектора:**
- Где хранятся допуски? В Pack-digital-platform (как DP.SC/DP.ROLE), в Local Gateway config, или в Neon?
- Один ли тип "доверенностей" или иерархия?

---

### Кирпич 4 — Окошко команд (операторский MCP)

**Суть:** три класса команд. Безопасные (поиск, чтение, подсчёт) — сразу. Изменения внутри хранилища — предпросмотр + "да". Необратимые (письмо, платёж, удаление во внешней системе) — предпросмотр + таймер 15 сек на отмену + явная пометка "нельзя вернуть". "Доверенность" на действия от имени пилота — отдельно от допуска к памяти.

**Открытые вопросы для архитектора:**
- Кто классифицирует команды? Агент, дворецкий или отдельный слой?
- Где хранится журнал всех команд (включая отменённые)?

---

## 3. Порядок пилота

Нельзя вешать замки на неготовую мебель → строгий порядок:

```
Фаза 1: Дворецкий (MCP-слой памяти) — учимся ходить
Фаза 2: Рабочий стол (структура памяти) — расставляем мебель
Фаза 3: Допуски по должностям — вешаем замки
Фаза 4: Окошко команд — даём ножницы (только после месяца без аварий на Ф1-Ф3)
```

---

## 4. Связь с темой 1 (Диспетчер)

Тема 1 встречи ("multi-agent в одном окне") предполагает Диспетчера, который открывает сессию и назначает роли агентам. Дворецкий (Кирпич 1) — это другой слой: посредник для **памяти**, а не для оркестрации агентов.

**Гипотеза:** Диспетчер сессий (кто) и Дворецкий памяти (что) — два разных компонента:
- Диспетчер открывает сессию → назначает агентам роли → агенты через Дворецкого читают/пишут в память
- Local Gateway координирует file-lock между этими агентами

Нужно подтвердить с архитектором.

## 4б. Находки архитектурного ревью (после peer-сессии)

**Перекрытие с существующим:** Local Gateway (DP.IWE.005) уже реализует часть Кирпича 1 (единая точка координации, идентификация агентов). Agent Dispatcher (iwe-agent-dispatcher.py) — маршрутизация задач. Hermes (WP-316) — агентская самопамять. "Дворецкий" = объединяющее имя для трёх независимых компонентов без общего интерфейса.

**Ошибка в порядке укладки:** Кирпич 1 (Дворецкий) маршрутизирует по доменам, которые создаёт Кирпич 2 (Структура). Технически Структура должна существовать раньше Дворецкого. **Предложение:** Дворецкий запускается в "плоском" режиме (без доменов, pass-through) → в Ф2 структура добавляется → Дворецкий обновляется для маршрутизации по доменам.

**Граница с Hermes (WP-316):** Hermes пишет в SQLite напрямую без посредника. Если 4 кирпичи покрывают всю агентскую запись в память пилота — это меняет архитектуру WP-316. Нужно явно разграничить: Hermes (агентская самопамять) и личное хранилище пилота — два разных хранилища или одно?

**Уровни прозрачности — ограничение:** статическое разбиение на карточки (общая / диагноз / оплата) не решает динамическую классификацию. Граница чувствительности зависит от контекста записи, не только от типа поля. Вариант: метка-уровень на поле (RBAC-стиль) или пилот рисует границу при создании записи.

**Не покрыто:** (а) жизненный цикл допуска — когда истекает, как отзывается; (б) роль Аудитора, читающего журнал дворецкого и формирующего отчёт пилоту; (в) масштабирование на 50+ пилотов (сейчас всё описано для одного).

## 5. Архитектурный разрыв: Президент vs Парламент

> **Это критическая секция.** Команда приняла Парламент-модель в встрече 18 (май 2026). Анализ показывает: предложенные 4 кирпича **реализуют Президента**, а не Парламент.

### Тест

**Тест Парламента:** «Может ли один агент в одиночку прочитать данные не своего домена?»

Применить к 4 кирпичам: Дворецкий (Кирпич 1) «знает структуру хранилища» и «выдаёт ровно то, что разрешено». Ответ: **да, Дворецкий может** — он знает все домены и единственный enforcement — политика промпта. **→ Президент.**

### Где именно Президент

| Кирпич | Проблема |
|--------|----------|
| 1 (Дворецкий) | Один агент знает структуру **всех** доменов. Ограничение — политика, не архитектура. |
| 2 (Структура) | Единое хранилище с общей схемой → Дворецкий знает где лежит всё. |
| 3 (Допуски) | Список хранит и проверяет сам Дворецкий — тот же Президент делегирует сам себе. |
| — | Верификатор (третий угол Парламента) **отсутствует полностью**. |

### Что нужно изменить для Парламента

**1. Разбить Дворецкого:** Дворецкий = реестр имён доменных агентов + маршрутизатор запросов. Он **не знает содержимого** ни одного домена. Запрос к домену "здоровье" → передаётся агенту здоровья, Дворецкий не читает ответ.

**2. Изолировать хранилища физически:** Вместо единого хранилища с ящиками — N отдельных хранилищ. Агент финансов физически не может вызвать API агента здоровья — не потому что написано "нельзя", а потому что у него нет токена.

**3. Перенести enforcement на платформу:** Допуски = токены/ACL на уровне API, не политика промпта Дворецкого.

**4. Добавить Верификатор:** Изолированный read-only компонент, читает только **журнал запросов** (не данные), проверяет соблюдение допусков, сигнализирует пилоту.

### Схема Парламента (целевая)

```
[Верификатор] — read-only журнал, изолирован, сигнализирует пилоту
      ↑ только логи
[Координатор] — реестр агентов + маршрутизация, НЕ читает данные доменов
      ↓ имя домена → агент
[Агент здоровья] | [Агент финансов] | [Агент обучения] | ...
      ↓ каждый читает только своё изолированное хранилище
[Хранилище здоровья] | [Хранилище финансов] | [Хранилище обучения] | ...
      ↑
[Enforcement] — платформенные токены/ACL, не политика промпта
```

Кирпич 4 (Окошко команд) сохраняется — это UX-паттерн. Команды "подписать от имени" идут через доменного агента, не через Координатора.
