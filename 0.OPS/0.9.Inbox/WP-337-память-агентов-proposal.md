# Доступ агентов к личной памяти пилота: архитектура Парламент

> **Источник:** пункты 3–6 оперативки ИТ 24 мая (приватность памяти, MCP-память, операторский MCP, дерево/граф).
> **Принятый принцип:** Парламент-модель (встреча 18, май 2026) — отказ доступа на уровне платформы, не промпта.
> **Цель:** согласовать до реализации.

---

## 1. Проблема

Личная память пилота — это разнородные данные: здоровье, финансы, рабочие заметки, обучение, проекты. У них разный уровень чувствительности и разные законные читатели. Тренер должен видеть расписание, но не анализы крови. Бухгалтер — платежи, но не диагнозы.

Сейчас это не выполняется архитектурно: когда агент обращается к личному хранилищу, он получает доступ ко всему — нет изоляции по доменам, нет платформенного контроля, нет аудита. Ограничения, написанные в промпте ("не читай финансы"), не дают гарантии: промпт можно обойти, сломать, неправильно интерпретировать.

Принятый принцип (встреча 18) — Парламент-модель: каждый агент физически не может прочитать данные вне своего домена. Не «написано нельзя», а «нет ключа».

---

## 2. Пять элементов (Парламент)

### Элемент 1 — Координатор (тонкий посредник)

**Что знает:** только имена доменных агентов и как к ним обратиться.
**Что НЕ знает:** содержимое ни одного домена, структуру ни одного хранилища.
**Роль:** принять запрос от внешнего агента → определить домен → передать доменному агенту → вернуть ответ, не читая его.

Аналогия: телефонный коммутатор — знает номера абонентов, соединяет, не слышит разговор.

Тест Парламента: «Может ли Координатор прочитать данные домена "здоровье"?» — Нет: у него нет токена ни одного домена. → **Парламент.**

Связь с существующим: Local Gateway (DP.IWE.005) в части маршрутизации между агентами — это Координатор без функции хранения данных.

---

### Элемент 2 — N доменных агентов

**Что:** один агент на домен — HealthAgent, FinanceAgent, WorkAgent, LearningAgent, ProjectsAgent.
**Что знает:** структуру и содержимое только своего домена (стопки, листы, ярлыки, уровни прозрачности).
**Что физически не может:** обратиться к API или хранилищу другого домена.

Аналогия: специалисты в отдельных кабинетах с несовместимыми карточками доступа — врач физически не попадёт в бухгалтерию, бухгалтер — в процедурную.

**Структура памяти живёт ВНУТРИ каждого доменного агента**, а не в общем пространстве. HealthAgent знает о стопках, листах, ярлыках и уровнях прозрачности своего домена. FinanceAgent знает то же — о своём.

**Многодоменная запись при создании делится сразу:**
Поход к зубному → при создании разрезается на карточки:
- Общая карточка + карточка диагноза → HealthAgent
- Карточка оплаты → FinanceAgent
- Карточки связаны сквозным ID, но физически в разных хранилищах

Пилот сам рисует границу при создании записи — доменные агенты помогают предложить разбивку.

**Резервный путь пилота:** пилот как владелец имеет прямой доступ к любому доменному агенту, минуя Координатора. Это не обход — это владелец, не агент.

---

### Элемент 3 — Платформенный замок

**Что:** токены / ACL на уровне API. FinanceAgent имеет токен только на FinanceAPI. HealthAgent имеет токен только на HealthAPI.
**Гарантия:** работает независимо от Координатора и промптов — даже если Координатор взломан или ошибается, платформа блокирует запрос без права у агента.

Аналогия: карточка доступа в здании — нет карточки, дверь не открывается. Это не правило — это физика замка.

Реализация: OAuth scope per domain agent, или отдельный MCP-сервер на каждый домен с изолированными credentials.

**Три уровня допуска** (выдаются через замок, не через политику):
- `read` — прочитать документы домена
- `write` — оставить запись в домене
- `act-as-owner` — действие от имени пилота (отдельный токен, выдаётся явно)

---

### Элемент 4 — Верификатор

**Что:** изолированный read-only компонент. Читает только **журнал запросов** (не данные). Не маршрутизирует, не хранит.
**Роль:** периодически проверяет соблюдение допусков, обнаруживает аномалии, сигнализирует пилоту.

Аналогия: камера видеонаблюдения с записью — видит кто заходил в какой кабинет и когда. Не читает документы. Только фиксирует движение.

Пример отчёта пилоту: «За неделю: HealthAgent обращался к здоровью 7 раз, FinanceAgent к финансам 3 раза. Аномалий нет.»

Связь с существующим: VR.R.002 (Аудитор) — аналогичная роль в платформе для compliance-аудита.

---

### Элемент 5 — Окошко команд

Логика из исходного предложения сохраняется, но с одной поправкой: **команды идут через доменного агента, не через Координатора.**

Три класса:
- **Безопасные** (читать, искать, считать) — сразу, без паузы
- **Изменения в хранилище** (переставить, отметить, дополнить) — предпросмотр + «да»
- **Необратимые** (письмо, платёж, внешнее удаление) — предпросмотр + таймер 15 сек + пометка «нельзя вернуть»

«Доверенность» (act-as-owner) — отдельный токен Элемента 3, не часть обычного допуска.

## 3. Порядок пилотного запуска

```
Шаг 1: Координатор в плоском режиме
        Один домен (например, "обучение"), pass-through без структуры.
        Учимся что запрос ходит через Координатора.

Шаг 2: Платформенный замок + первый доменный агент
        Первый настоящий доменный агент с изолированным токеном.
        Нельзя добавлять агентов без замка — иначе он бесполезен.

Шаг 3: Остальные доменные агенты (по одному)
        Каждый со своим токеном и изолированным хранилищем.
        Тест: новый агент физически не может читать уже существующие домены.

Шаг 4: Верификатор
        Включается после того как все агенты работают — есть что проверять.

Шаг 5: Окошко команд
        Только после месяца работы Шагов 1-4 без аварий.
        Сначала безопасные команды, потом необратимые.
```

Принцип: нельзя вешать замок (Шаг 2) без того, на что его вешать (Шаг 1). Нельзя проверять (Шаг 4) то, что ещё не работает (Шаг 3). Нельзя давать ножницы (Шаг 5) до стабильной работы всего остального.

---

## 4. Связь с Диспетчером сессий

Диспетчер, открывающий сессию (тема 1 оперативки 24 мая), вписывается в эту схему чисто:

```
Пилот
  └─→ Диспетчер сессий (назначает роли агентам, открывает контекст)
         └─→ Координатор (маршрутизирует к доменным агентам по запросу)
                ├─→ HealthAgent → [здоровье-хранилище]
                ├─→ FinanceAgent → [финансы-хранилище]
                └─→ ...

Local Gateway — координирует file-lock между агентами сессии
Верификатор — читает журнал всех обращений
```

Диспетчер сессий знает **роли агентов** (Портной, Аналитик, Тренер), не домены памяти. Координатор знает **домены памяти**, не агентские роли. Это разные оси, разные компоненты.

---

## 5. Проверка тестом Парламента

| Компонент | «Может прочитать чужой домен?» | Вывод |
|-----------|-------------------------------|-------|
| Координатор | Нет — нет токенов доменов | ✅ |
| HealthAgent | Нет — токен только на HealthAPI | ✅ |
| FinanceAgent | Нет — токен только на FinanceAPI | ✅ |
| Верификатор | Нет — read-only на журналы, не на данные | ✅ |
| Диспетчер сессий | Нет — знает роли, не домены | ✅ |
| Пилот (владелец) | Да — прямой доступ к любому доменному агенту | ✅ (владелец, не агент) |

**Итог: архитектура является Парламентом.**
