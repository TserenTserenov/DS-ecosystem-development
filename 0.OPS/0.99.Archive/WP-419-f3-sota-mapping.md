# Ф3: Сопоставление SOTA с текущей базой кодирования IWE

## Дорожка 1 — ДИЗАЙН (корректность): что берём из SOTA

| SOTA-приём | Что даёт | Где применим у нас | Вердикт |
|------------|----------|--------------------|---------|
| **ISO/IEC 11179 — lifecycle administered items** | Жизненный цикл кода + Registration Authority (владелец) + разделение «схема классификации ≠ идентификатор» | Наш lifecycle proposed→active→deprecated→retired = упрощение ISO. Owner-поле = Registration Authority — прямое лекарство от COL-01/02 (корень = нет владельца namespace). | **ВЗЯТЬ:** lifecycle + обязательный owner + правило «не вшивать изменчивую классификацию в ID» |
| **Фасетная классификация (Ранганатан, PMEST)** | Независимые ортогональные оси вместо одной жёсткой иерархии | «тир · дом · поколение» (WP-415) = уже фасеты. COL-01 (F1-F9 ↔ FX1-FX9) = смешение двух фасетов в пересекающихся диапазонах. | **ВЗЯТЬ:** «критерии хорошей оси» Ф1 = правила фасета (ортогональность, взаимоисключение внутри фасета, явное имя оси) |
| **DDD bounded contexts (SOTA.001)** | Один код = разный смысл в разных контекстах; контекст владеет своим namespace | COL-03..08 = «один код, разный bounded context». Вердикт COL-06/07/08 (допустимое дублирование при явном namespace) = ровно это. | **ВЗЯТЬ:** реестр объявляет свой bounded context (owner+scope); cross-context ссылка обязана квалифицировать namespace |
| **Identifier design (semantic vs opaque)** | Смысловой ID читаем, но хрупок к переклассификации; opaque стабилен | IWE = смысловые ID как данность (консенсус аудита). Не менять. | **ВЗЯТЬ частично:** держим смысловой ID + митигация дрейфа (tombstone+alias) + design-правило «ID стабилен, изменчивая классификация — в поле, не в коде» |
| **SKOS (controlled vocabularies)** | altLabel (синонимы), deprecation-флаг; post-hoc, не write-prevention (Ф2) | altLabel = наш alias; deprecation = наше retired-состояние | **ВЗЯТЬ лёгкое:** alias + deprecation-маркер. Полный SKOS/RDF — НЕТ (scope-guard, новый инструмент) |

| SOTA-приём | Что даёт | Где применим у нас | Вердикт |
|------------|----------|--------------------|---------|
| **Policy-as-code / GitOps (OPA, Conftest, checkov)** | Декларативные политики, принуждаемые в CI против текстовых файлов = ровно наш E2 | Наш E2 (commit-guard, напр. WP-REGISTRY drift-guard) = policy-as-code. Закрытый Ф2 вопрос: это ближайший SOTA-аналог git-реестров. | **ВЗЯТЬ модель, не инструмент:** E2 как policy-as-code; OPA/Conftest — концептуальный референс; реализация через наши хуки (bash/python), без нового tool |
| **Schema Registry (Confluent) — compatibility + версии** | schema_version + режимы совместимости; даже Confluent не закрывает все write-пути (Ф2) | `schema_version` в каждом реестре. Режимы совместимости → у нас «deprecation + переходный период». | **ВЗЯТЬ:** schema_version (semver: breaking=major) + рецепт миграции |
| **Semantic versioning** | Версионирование эволюции схемы | Эволюция реестров | **ВЗЯТЬ:** semver-семантика для schema_version |

## Отбор для метода Ф4 (что реально входит)

1. **Обязательный owner** у каждой схемы (= Registration Authority ISO 11179). Корень коллизий — отсутствие владельца namespace.
2. **Фасетная дисциплина осей:** ось ортогональна, имеет имя, внутри взаимоисключающа; не overload одного диапазона между фасетами.
3. **Bounded context = namespace:** cross-context ссылка квалифицирует код (`P5 (DP.SC.172)`).
4. **ID стабилен, классификация — в поле** (не вшивать изменчивое в код); дрейф митигируется tombstone+alias+переходный период.
5. **schema_version (semver)** + рецепт миграции в каждом реестре.
6. **Принуждение по оси E0-E3** (ядро, без изменений): policy-as-code (E2) через наши хуки — целевой механизм для новых схем там, где структурно.

## Что НЕ взяли и почему

- Полный ISO/IEC 11179 (8 частей) — избыточно для текстовых git-реестров; берём lifecycle + owner + classification-separation.
- SKOS/RDF-тристор, SHACL — требует нового инструмента (нарушает scope-guard); берём только идею alias+deprecation.
- Opaque/непрозрачные ID — meta-РП уровня экосистемы (вне scope WP-419, консенсус аудита).
- Внешний OPA-движок — берём модель policy-as-code, реализуем существующими хуками.

## Открыто для Ф4

- Условие (в) метода переформулировать в два независимых вопроса (structural/semantic) — НЕ «два слоя одного контракта».
- E2-drift-guard каталога + governance метода — target-state, вне MVP P3.
