# ADR-IWE-017: Архитектура чистого MCP-шлюза (Вариант A+G)

**Статус:** Принято  
**Дата:** 2026-06-10  
**РП:** WP-410  
**АрхГейт:** пройден (Ф1 peer-сессии 2026-06-10-10-wp410-mcp-gateway)

---

## Контекст

Шлюз `gateway-mcp` смешивает три разные обязанности:
1. MCP fan-out к knowledge/dt/personal (уже чисто, JWT)
2. Собственные обработчики 12 инструментов через shared-secret к внутренним сервисам (P1+P2)
3. Server-to-server трафик (GitHub-webhook, OAuth)

**P1 (безопасность):** shared-secret хрупок — один утёкший пароль позволяет притвориться любым пользователем через `X-User-Id`.  
**P2 (архитектура):** шлюз знает прикладную логику — любое изменение бэкенда требует правки шлюза.

Принцип-арбитр (Андрей Смирнов, 07.06.2026): «Посмотри на конфиги шлюза. Если там только адреса сервисов — правильный шлюз. Если там БД, токены, shared-secret, что угодно кроме адресов — шлюз взял прикладную логику.»

---

## Решение

Целевая архитектура: **Вариант A + Вариант G**.

### Вариант A — сервисы становятся MCP-серверами с Ory JWT

Каждый сервис с user-path логикой добавляет MCP-интерфейс и верифицирует JWT самостоятельно (через JWKS Ory, как уже делают knowledge/dt/personal). Шлюз убирает свои обработчики и shared-secret к этим сервисам.

### Вариант G — декларативный реестр маршрутизации

Шлюз не содержит названий инструментов в коде. Таблица `prefix → service URL` в registry.yaml. Новый сервис = строка в таблице, не правка кода шлюза.

---

## Отклонённые альтернативы

| Вариант | Причина отклонения |
|---------|-------------------|
| B (JWT-фасад) | Лечит P1, оставляет P2 — шлюз по-прежнему жирный |
| E (все sidecar) | N сервисов = N sidecar = N точек правки; паттерн неоднороден; доп. hop |
| F (убрать шлюз) | Стратегическая цель, но два барьера: MCP discovery не стандартизирован + клиентский UX T1-T3 требует единого коннектора |
| H (mTLS) | Лечит только P1, оставляет P2 |

**F остаётся стратегической целью.** Переход к F — когда оба барьера упадут одновременно.

---

## Исключение: Вариант E (sidecar) как exception

E применяется к конкретному сервису, только если выполняется хотя бы один из 4 критериев:
1. Сторонний сервис вне нашего периметра
2. Команда-владелец явно отказалась от MCP-миграции
3. Frozen API (нет релизного цикла для добавления endpoint)
4. Vendor-controlled код — нельзя добавить MCP endpoint без изменения vendor-кода

При применении E: explicit decision в этом ADR (или дочернем) + 90-дневный таймбокс на переход к A.

**Текущий E-exception:** `hermes_chat` → Hermes runtime (Railway, внешний сервис, `HERMES_API_KEY`). Критерий 1 выполнен. Срок перехода к A: 90 дней от первого применения.

## Классификация вызовов (Ф2, верифицирована)

| Категория | Кол-во | Действие | Фаза |
|----------|--------|----------|------|
| MCP fan-out (уже чисто) | 60+ | без изменений | - |
| User-path shared-secret | 12 | → A (MCP + JWT) | Ф4а, Ф4б |
| hermes_chat (E-exception) | 1 | E sidecar, 90d таймбокс | Ф4б |
| User-path уже JWT | 3 | без изменений | - |
| Gateway-агрегаторы (package deal) | 4 | → A в learning-context-service | Ф4а |
| Delivery channels | 2 | exception (ArchGate) | Ф8 |
| Server-to-server | 5 | увести из шлюза | Ф7 |

**Находка верификации:** `/github/install GET` — гибридный маршрут (пробует JWT пользователя). При Ф7: нужен redirect-endpoint на стороне github-integration-service, не просто удаление.

## Риски и митигация

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Package deal агрегаторов затянется | средняя | Агрегаторы = первый приоритет Ф4а |

| G-реестр без schema validation | низкая | JSON Schema для registry.yaml + CI check |

---

## Последствия

- Шлюз становится чистым маршрутизатором: конфиг = только адреса сервисов + проброс JWT
- Каждый сервис отвечает за свою авторизацию (zero-trust)
- Shared-secret (`*_SHARED_SECRET`) уходят из шлюза в Ф6
- G-реестр заменяет hardcoded routing по имени инструмента
