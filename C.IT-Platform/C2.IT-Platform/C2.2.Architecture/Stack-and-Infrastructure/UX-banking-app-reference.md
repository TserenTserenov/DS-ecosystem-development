# UX-референс банковского приложения для Web App / Activity Hub

> **Зачем.** `DP.IWE.001` уже даёт текстовую метафору «IWE-дашборд похож на банковский». Этот документ — не повтор метафоры, а конкретная таблица «банковский UX-паттерн → существующий источник данных в IWE», подготовленная как задел для Web App (сейчас не начат, Ф4 WP-135 блокирован стартом Web App — см. WP-73 Ф1.1). Получатель — Инга при старте Web App Phase 1.
> **Архитектурная граница.** Любой экран Web App читает данные только через единый Read API (`DP.SC.031`, `dt_*` tools Gateway) — не напрямую в Neon. Любой новый виджет, показывающий персональные данные, обязан писать `dt_view_requested` (`DP.SC.032`).

## 1. Метод: два уровня готовности

Семантический аудит (пир-сессия 2026-07-24) показал, что банковский UX-паттерн несёт не только форму, но и обязательную семантику сущности (баланс = атомарное число; операция = сумма + статус + контрагент/категория). Проверка по коду показала, что у IWE это выполняется для **токенов/баллов**, но не для **активности (Activity Hub)** — разные разделы ниже.

## 2. Готово к UX — токены/баллы (`rewards.*`)

Модель уже банковская, не декорация — можно проектировать экран прямо сейчас.

| Банковский паттерн | Источник в IWE | Поля |
|---|---|---|
| **Баланс на главном экране** | `rewards.point_balances.points` (source of truth), `.earned_total` (lifetime, BEFORE-триггер) | `account_id, points, earned_total` |
| **История начислений (credits)** | `rewards.applied_events` | `event_id, event_type, base_amount, dom_mult, qual_mult, streak_mult, effective, cap_truncated, applied_at` — готовая детализация «почему именно такая сумма» |
| **История списаний (debits)** | `rewards.redeemed_events` | `payment_id, points_amount, discount_rub, purpose, payment_source, status, product_code` |
| **Статус операции («в обработке» / «исполнено»)** | `redeemed_events.status` — двухфазный `reserved → confirmed` (WP-327) | уже строже многих банков — резерв виден отдельно от подтверждения |
| **Кешбэк / программа лояльности** | `loyalty_pool_config`, множители `activity_domain_multipliers`, `qualification_multipliers` | текстовая аналогия уже в `DP.IWE.001`; здесь — конкретные таблицы-источники для UI множителей |
| **Дневной лимит («траты в день»)** | `get_user_daily_cap()` (action_cap × K-множитель ступени) | готово к отображению как «доступно сегодня: N из M» |

**Для UI:** список операций = `applied_events` (credit) ∪ `redeemed_events` (debit, только `status='confirmed'` — резервы/откаты не показывать пользователю, см. существующий код `/points`), отсортировано по времени. Кредит/дебет — уже различимые таблицы, не нужен единый тип «транзакция» на уровне БД, только на уровне UI-компонента.

## 3. Нужен семантический аудит перед UX — Activity Hub / R6-R7

`learning.domain_event` — плоская лента: `event_type, account_id, occurred_at, payload`, агрегация только `COUNT(*)`/`GROUP BY` (см. `engagement_collector.py`, `check_attribution_health()`). Нет `amount`, `status`, `purpose` — наложить паттерн «список транзакций с суммой» на неё сейчас = красивая оболочка без содержания.

**Что нужно сделать ДО UX-дизайна этой части** (не входит в объём этой сессии — отдельная фаза):
1. Определить, какие агрегаты (не сырые события) имеют смысл как «карточка» — например, недельный срез коммитов/coding_time/РП, а не построчный лог каждого события.
2. Решить, нужен ли Activity Hub'у собственный «эффективный итог» по аналогии с `applied_events.effective` (например, через веса доменов — `activity_domain_multipliers` уже применяются к rewards, не обязательно к самому Activity Hub).
3. Только после этого — паттерн «прогресс-бар к цели» (milestones 7/14/30/60/90, marathon_steps) и «дашборд состояния» (характеристики R6: cp.rhy/wld/skl/iwe/int/agt) можно проектировать предметно, не абстрактно.

## 4. Готово частично — уже есть в UI бота

- `/progress` — де-факто compact dashboard (streak, календарь, QA, feed, assessment) — 6 секций, но не всё покрытие Activity Hub (см. WP-135 resolved-externally анализ — ~30% собранных данных видно пользователю).
- `/mydata` — tier-aware метрики + AI-объяснения.
- Push-уведомления — инфраструктура (`conversion_events`, триггеры C1-C7, WP-5) есть, но не оформлена как «уведомление о списании/зачислении» в банковском смысле — предложения-триггеры (feed→ЛР, goal matching), не операции по счёту.

Web App-версия этих экранов не «рисуется с нуля» — она читает то же самое через `DP.SC.031`, просто в браузере вместо Telegram.

## 5. Future / backlog — паттерны без данных сейчас

| Паттерн | Чего не хватает |
|---|---|
| Прогноз темпа развития («сколько накопится к сроку») | Нет предиктивной модели поверх R6/R7 — открытый архитектурный вопрос, не просто UI |
| Персонализированные рекомендации как push («вам может подойти вклад») | Логика C5/C6 (feed→ЛР, goal matching) есть, но не оформлена как отдельный notification-канал, отличный от общих сообщений бота |
| Категоризация «трат» баллов по смыслу (как категории в банке: еда/транспорт) | `redeemed_events.purpose`/`product_code` уже это частично покрывают — нужна проверка, достаточно ли текущих значений `purpose` для читаемой категоризации в UI, не заводить новую таксономию с нуля |

## 6. Итог для Инги (при старте Web App Phase 1)

- Экран «Баланс + история операций» — проектировать первым, данные полностью готовы (§2).
- Экран «Активность/прогресс» — требует сначала агрегатного слоя поверх `domain_event` (§3), не берите паттерн «транзакция» буквально.
- Все запросы — через `dt_*` Gateway (`DP.SC.031`), не напрямую в Neon; каждый просмотр персональных данных пишет `dt_view_requested` (`DP.SC.032`).
