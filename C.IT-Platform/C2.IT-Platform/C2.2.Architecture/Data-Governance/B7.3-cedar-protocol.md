# B7.3 Протокол доступа к личным данным (Cedar-семантика)

> **Уровень документа:** governance (программа безопасности, WP-212 ФС1). Здесь — модель политик и нормативные правила. Конкретные RLS-предикаты, column grants и конфигурация Gateway — исполнительный уровень (WP-544), сюда не входят (граница закреплена пир-сессией `MC-sessions/2026-09/12/2026-09-12-09`).

## 1. Scope & Status

- **Цель:** единые, проверяемые правила «кто (principal) может делать что (action) с какими личными данными (resource) при каких условиях (context)» — поверх уже существующих механизмов, без внедрения Cedar-движка. Cedar здесь — язык описания политик, не runtime.
- **Статус:** draft v2 (после двух ревью пир-сессии: Kimi C1-C2/H1-H3/M1-M4, Codex AC1-AC4). Фаза ФС1 активирована пилотом 12.09.2026 (до этого pending с 16.06: директива «Cedar — фаза WP-212, не отдельный РП»).
- **Границы:** только классы PII и payment_credentials из B7.3.1 (+ пограничные secrets∩PII OAuth-токены). Чистые secrets — вне scope (их протокол — брокер секретов, WP-544 Д27).
- **Не покрывает:** реализацию (SQL, конфиги, деплой) — см. §7 Traceability → intake WP-544.

## 3. Policy Model (сущности)

- **Principal** (кто): `User` (владелец данных, идентификатор ory_id), `ServiceAccount` (воркер/ETL/MCP-сервис), `Admin` (пилот/DBA), `Bot` (канальный клиент — телеграм-бот, действующий от имени конкретного пользователя, обязан нести `context.on_behalf_of`), `Auditor` (audit_reader, read-only).
- **Action** (что): `read`, `decrypt`, `write`, `delete`, `export`, `aggregate`.
- **Resource** (над чем): класс данных × носитель. Классы — по B7.3.1 §1: `PII`, `PaymentCredentials`, пограничный `OAuthToken` (secrets∩PII), плюс служебный `AuditLog`. Атрибуты: `owner` (ory_id субъекта), `sensitive_fields`, `layer` (L2 Aisystant — единственный слой, где PII разрешён вне владения пользователя).
- **Context** (при каких условиях) — полный словарь атрибутов, используемых в §5:
  - `purpose` — закрытый список B7.3.3 §2; расширение только через §8;
  - `reference_id` — единый идентификатор основания (ticket-id / incident-id / audit-id / erasure-request-id; тип различается по purpose);
  - `justification_validated` — результат проверки основания по INV-6 (bool);
  - `consent` — действующее согласие субъекта (bool, из consent-реестра, тоже под INV-6);
  - `k` — размер минимальной группы в агрегате (int);
  - `individual_fields` — содержит ли результат индивидуальные поля (bool);
  - `destination` — приёмник при export: `internal` | `anthropic` | `openai` | `langfuse` | `yookassa` | `external_other`;
  - `minimized` — прошла ли выборка минимизацию перед внешней передачей (bool);
  - `dpa` — подписан ли DPA с приёмником (bool);
  - `on_behalf_of` — ory_id пользователя, от имени которого действует Bot/интеграция.

**Соответствие словарям-источникам (сверено 12.09.2026 по текстам файлов):** Principal-словарь = `actor_kind` B7.3.3 §1 (`user`, `service_account`, `admin`, `bot`) + `Auditor` (роль audit_reader B7.3.3 §6); Action = `operation` B7.3.3 §1 (`read`, `decrypt`, `write`, `delete`, `export`) + `aggregate` (расширение под B7.3.1 §3.5 — внести в B7.3.3 §1 синхронной правкой при принятии этого документа); все purpose-коды §5 (`user_self_view`, `user_request`, `service_routine`, `internal_analytics`, `gdpr_erasure`, `support_ticket_resolution`, `legal_compliance`, `security_incident`, `compliance_audit`, `migration`) входят в закрытый список B7.3.3 §2.

## 4. Таксономия PII-ресурсов

По B7.3.1 §1 и §4 (карта таблиц) — без перечисления таблиц (это исполнительный уровень), по видам ресурса:

| Ресурс | Класс | Особенность |
|--------|-------|-------------|
| Идентификаторы человека (email, telegram_id, ory_id, ФИО) | PII | ory_id — PII, но не secret; telegram_id ≠ chat_id канала |
| Поведенческие события (user_events с user_id, метрики активности) | PII | производные (embeddings личных документов) наследуют класс |
| Профиль/цифровой двойник (агрегированный расчётный профиль) | PII | агрегированность не снижает класс: профиль привязан к человеку |
| Платёжные атрибуты поведения (amount, история платежей) | PII | НЕ payment_credentials — с ними нельзя списать деньги (B7.3.1 граница) |
| Платёжные инструменты (saved_payment_tool, autopay credential) | PaymentCredentials | самый строгий режим: POL-05 |
| OAuth-токены пользователя | OAuthToken (secrets∩PII) | владение — пользователь (RLS), защита — как secrets (шифрование); двойная природа B7.3.1 §1 |

## 5. Policy Catalog (нормативный)

### 5.0 Policy Evaluation Contract (правила вычисления)

1. **Precedence:** явный `forbid` сильнее любого `permit`; при отсутствии подходящего `permit` — deny (default deny).
2. **Fail-closed на неполном контексте:** отсутствующий, пустой или невалидируемый атрибут, требуемый политикой (например, `purpose`, `justification_validated`, `on_behalf_of` у Bot), эквивалентен deny — никогда не «пропустить и посчитать позже».
3. **Обязательные атрибуты по действию:** `read/decrypt/write/delete` над PII → `purpose`; `aggregate` → `purpose`, `individual_fields`, `k` или `consent`; `export` → `purpose`, `destination`, `minimized`/`dpa`; любой admin-доступ → `reference_id` + `justification_validated`.
4. **Нормализация enum:** значения `purpose`, `destination`, `actor_kind` сравниваются после канонизации (нижний регистр, закрытые списки §3); неизвестное значение = deny, не «прочее».

### 5.1 Правила

```cedar
// POL-01a: владелец читает своё
permit (principal is User, action in [Action::"read", Action::"export"], resource)
when { resource.owner == principal.id
       && context.purpose in ["user_self_view", "user_request"] };

// POL-01b: Bot действует строго от имени владельца
permit (principal is Bot, action in [Action::"read", Action::"export"], resource)
when { resource.owner == context.on_behalf_of
       && context.purpose in ["user_self_view", "user_request"] };

// POL-02: чужое чтение пользователем запрещено безусловно
forbid (principal is User, action, resource)
when { resource.owner != principal.id };
forbid (principal is Bot, action, resource)
when { resource.owner != context.on_behalf_of };
// исключений на уровне User/Bot нет; поддержка — это Admin с основанием (POL-06)

// POL-03: сервис работает с PII только с декларированной целью
permit (principal is ServiceAccount, action in [Action::"read", Action::"write"], resource is PII)
when { context.purpose in ["service_routine", "internal_analytics", "gdpr_erasure"] };
// без purpose — deny по контракту §5.0 п.2; bulk-паттерны ловят детекторы A1/A2

// POL-04: агрегация — тоже только с целью
permit (principal is ServiceAccount, action == Action::"aggregate", resource is PII)
when { context.purpose == "internal_analytics"
       && context.individual_fields == false
       && (context.k >= 10
           || (context.consent == true && context.justification_validated == true)) };

// POL-05: платёжные инструменты — только авторизованный платёжный конвейер
permit (principal is ServiceAccount,
        action in [Action::"read", Action::"decrypt", Action::"write"],
        resource is PaymentCredentials)
when { principal.pipeline == "payment" && context.purpose == "service_routine" };
// export платёжного инструмента: единственный легитимный приёмник — YooKassa (назначение инструмента)
permit (principal is ServiceAccount, action == Action::"export", resource is PaymentCredentials)
when { principal.pipeline == "payment"
       && context.purpose == "service_routine"
       && context.destination == "yookassa" };
forbid (principal, action == Action::"export", resource is PaymentCredentials)
when { context.destination != "yookassa" };
forbid (principal is User, action, resource is PaymentCredentials);
forbid (principal is Bot, action, resource is PaymentCredentials);
// сырое чтение инструмента пользователю не нужно: продукт показывает masked-представление (PII-класс), не credential

// POL-05a: админ и платёжные инструменты — только инцидент с валидированным основанием
permit (principal is Admin, action == Action::"read", resource is PaymentCredentials)
when { context.purpose == "security_incident"
       && context.reference_id != ""
       && context.justification_validated == true };
// каждое срабатывание → алерт A8 (INV-5), см. §7

// POL-06: админ-доступ к PII — только с целью и валидированным основанием
permit (principal is Admin, action in [Action::"read", Action::"decrypt"], resource is PII)
when { context.purpose in ["support_ticket_resolution", "legal_compliance",
                           "security_incident", "compliance_audit", "migration"]
       && context.reference_id != ""
       && context.justification_validated == true };

// POL-07: аудитор — read-only к аудит-логу, не к самим PII
permit (principal is Auditor, action == Action::"read", resource is AuditLog);
forbid (principal is Auditor, action, resource is PII);

// POL-08: удаление — только по контракту erasure
permit (principal is ServiceAccount, action == Action::"delete", resource is PII)
when { context.purpose == "gdpr_erasure"
       && context.reference_id != ""
       && context.justification_validated == true };  // erasure-request существует и не отозван; процедура — WP-554 (H-306)

// POL-09: внешняя передача PII (LLM/трейсы) — цель + минимизация; аналитика вовне — только с DPA
permit (principal is ServiceAccount, action == Action::"export", resource is PII)
when { context.purpose in ["service_routine", "internal_analytics"]
       && context.destination in ["anthropic", "openai", "langfuse"]
       && context.minimized == true };
forbid (principal, action == Action::"export", resource is PII)
when { context.destination == "external_other" && context.dpa == false };

// POL-10: OAuth-токены — двойная природа
permit (principal is ServiceAccount, action == Action::"decrypt", resource is OAuthToken)
when { context.purpose == "service_routine"
       && resource.owner == context.on_behalf_of };
// чтение токена возможно только от имени его владельца (integration call)
```

## 8. Процедура изменения политики

1. **Предложение:** новая/изменённая политика оформляется PR к этому файлу: правило в Cedar-нотации + минимум один негативный тест-вектор + строка Traceability (все колонки §7).
2. **Проверка:** (а) не нарушает инварианты §2 и контракт §5.0; (б) purpose-словарь расширяется только здесь и в B7.3.3 §2 синхронно; (в) класс ресурса сверен с B7.3.1.
3. **Утверждение — правило двух ключей.** Изменения высокого риска (ослабление forbid, новый permit к PaymentCredentials/OAuthToken, расширение admin-доступа, новый purpose) требуют ДВУХ независимых утверждений: пилот + независимый security/audit-ревьюер (внешний ревьюер B7.11 или назначенный аудитор; до его появления — второй агент в холодном контексте с записью в журнале сессии). Низкорисковые (новый негативный тест, уточнение формулировки, ужесточение) — пилот единолично. Разделение обязанностей — продолжение INV-2 на мета-уровне.
4. **Emergency-change:** при активном инциденте допустимо временное исключение по решению пилота с обязательными атрибутами: `expiry` (TTL, максимум 14 дней), причина, ссылка на инцидент. Post-factum ревью на ближайшем posture-аудите; по истечении TTL исключение снимается автоматически (rollback — состояние до изменения), продление = новое полное утверждение по п.3.
5. **Исполнение:** intake в WP-544 по гейту WP-212 §Операционная модель (запись в реестре Ф1, возврат отклонённого с тегом).
6. **Приёмка:** негативные тест-векторы §6 воспроизведены на реализации; evidence-артефакт из §7 приложен; posture обновлён.
