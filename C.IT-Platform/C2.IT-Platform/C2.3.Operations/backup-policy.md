# Политика резервного копирования IWE

> **Source:** согласовано на peer-сессии BAK1 (`DS-my-strategy/sessions/2026-06/2026-06-18-09-backup-audit/report.md`), реализовано в WP-7 BAK1-F2.
> **Назначение:** что бэкапится, как часто, как проверить, что делать при сбое.

## 1. Три уровня резервирования

| Уровень | Канал | Статус | Проверка |
|---|---|---|---|
| 1 | iCloud-архивы (`IWE-backup-*.tar.gz`) | основной, работает | `scripts/iwe-backup-check.sh` |
| 2 | Локальные копии `.backups/` | legacy / fallback | тот же скрипт, раздел 2 |
| 3 | Git-репозитории на GitHub | живой backup кода и истории | тот же скрипт, раздел 3 (dirty/unpushed) |
| 4 (offsite) | цех-1 → restic → Backblaze B2 | работает, см. §4 | `systemctl status restic-backups-*.service` на цех-1 |

## 2. Ротация и пороги

- Архив создаётся `FMT-exocortex-template/scripts/backup-icloud.sh`.
- Свежесть: ⚠️ предупреждение при возрасте >7 дней, ❌ критично >14 дней (настраивается через `--warn-days`/`--critical-days`).
- Ротация: минимум 2 архива в iCloud одновременно — меньше означает, что старые копии не сохраняются.
- Целостность: `tar -tzf` smoke-тест (одно чтение архива без распаковки) — пропускается, если архив является iCloud-заглушкой (файл размером 0 КБ локально, физически не скачан из-за "Optimize Mac Storage").
- Полнота: количество файлов в последнем архиве сравнивается с эталонным значением (baseline, `DS-my-strategy/current/backup-baseline.json`) — если текущий архив содержит <80% от baseline, это тревога о неполном бэкапе.
- Baseline устанавливается вручную командой `bash scripts/iwe-backup-check.sh --reset-baseline` после осознанного крупного изменения объёма данных (не автоматически — иначе баг "тихо подстроился под деградацию" останется незамеченным).

## 3. Восстановление после сбоя (Restore)

1. **Определить последний рабочий архив.** `bash scripts/iwe-backup-check.sh` — секция 1 покажет имя, возраст, результат smoke-теста.
2. **Скачать архив физически.** Если iCloud показывает заглушку (0 КБ) — открыть файл в Finder (принудительная загрузка из облака) перед распаковкой.
3. **Проверить целостность перед распаковкой.** `tar -tzf IWE-backup-YYYYMMDD-HHMM.tar.gz` — не должно быть ошибок.
4. **Распаковать во временную директорию**, НЕ поверх текущего `~/IWE/` (не затирать потенциально живые несбойные данные без сверки).
5. **Для кода** — репозитории также существуют на GitHub (уровень 3): `git clone` — актуальнее архива для всего, что было запушено.
6. **Для данных, которых нет в git** (memory/, `.env`, локальные конфиги) — только из архива уровня 1/2 или offsite (уровень 4, когда будет настроен).

**Не восстановлено этой политикой:** реальный тест полного restore (распаковать архив, убедиться что каждый git-репозиторий внутри валиден) — известный открытый пункт из BAK1 (см. `report.md §5`), не входил в BAK1-F2.

## 4. Offsite-канал

**Уже настроено и работает** — обнаружено при закрытии BAK1-F2 (2026-07-06): dedicated-сервер «цех-1» независимо от BAK1 получил restic-бэкап в Backblaze B2 через другой рабочий продукт (WP-138), декларативно описанный в `iwe-server-config/modules/backup.nix`. BAK1-сессия (18 июня) не знала об этой инфраструктуре и оставила offsite открытым вопросом — по факту вопрос уже был закрыт другой работой (см. Стоп-лист «результат достигнут иначе»).

**Что бэкапится на цех-1 (systemd timer, ежедневно, Helsinki-время):**

| Задание | Источник | Назначение (B2) | Расписание | Ротация |
|---|---|---|---|---|
| `restic-backups-neon-dbs` | `pg_dump` всех Neon-БД по списку в `/etc/restic/neon-connections` | `b2:<bucket>:neon-dbs` | 03:00 | 7 daily / 4 weekly / 12 monthly |
| `restic-backups-local-files` | `/home/tseren` (включая `IWE/`, кроме `.git`/`node_modules`/кэшей) + `/etc/restic` (секреты restic) | `b2:<bucket>:local` | 03:30 | 7 daily / 4 weekly / 3 monthly |

**Проверка живости:** `ssh tsekh-1 systemctl status restic-backups-neon-dbs.service restic-backups-local-files.service` — оба должны показывать последний запуск `code=exited, status=0/SUCCESS`. Успешный дамп БД дополнительно пингует heartbeat в Better Stack (если настроен `/etc/monitoring/backup-heartbeat-url`).

**Ограничение:** копия `IWE/` на цех-1 — это снимок рабочего дерева файлов (без `.git`), не полная git-история. Git-история резервируется отдельно через уровень 3 (репозитории на GitHub, см. §1). Секреты (`/etc/restic/password`, `/etc/restic/b2-env`, `/etc/restic/neon-connections`) создаются вручную на сервере, не хранятся в git — при полном восстановлении сервера их нужно будет ввести заново.

## 5. Ограничение: секреты и приватность репозиториев

**Архитектурная заметка (не работа, ограничение).** Любой репозиторий, в истории которого могут быть ключи, пароли или токены (например, конфигурация серверов), можно заливать на GitHub **только как приватный репозиторий**. Проверка истории на секреты — обязательный шаг перед первым пушем orphan-репозитория, не разовая рекомендация.

`.mcp.json` и подобные файлы с токенами не входят в эту политику — они под отдельным РП (см. WP-399, владелец там).
